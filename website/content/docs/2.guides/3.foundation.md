title: Ground rules (Foundation)

---

The ground rules are the project's Foundation: what it is for, what it is built with, how its code is shaped and how the team works on it. Every agent that writes a proposal, spec or design reads them first, so it builds on your decisions instead of inventing its own. This page covers the questions, how answers are proposed, and where they are stored.

## Why before the first change

Without ground rules, each change's agent picks its own framework, layering and naming, and the next change picks differently. spec-tacular asks once, up front, and refuses to start a change while required answers are missing. In the TUI the overview says `Settle the ground rules first — f continues them`. From the shell, the first artifact of a change is refused:

```
Answer them in <project>/spec-tacular/foundation, then try again.
See what is outstanding with: spec-tacular foundation
```

Open the ground rules with :key-cap{k="f"} on the overview, or from the start screen during setup.

## The questions

The questions come in four groups, one file each:

| Group | What it covers |
| --- | --- |
| Domain | What you are building, and for whom. Asked first |
| Stack | What it is built with |
| Architecture | How the code is shaped, and which way dependencies point |
| Conventions | How the team works on it |

On a new project, only what can be answered on day one is asked. The rest is proposed or left for later:

| | Questions |
| --- | --- |
| Asked | What the system is for, and who uses it |
| Proposed from the vision or the domain (⇐, enter confirms) | the core terms · language and runtime · framework · datastore · package manager and tools · architecture style · layers and which may depend on which · where business rules live · naming · what a test must cover |
| Left for later | domain invariants · out of scope · what is ruled out · error handling · configuration and secrets · code review · comment style · what newcomers get wrong |

On an existing project, all nineteen questions are asked, domain first.

## Asked, proposed, or decided later

Each question lists its choices. One of them is pre-selected, so most of the setup is reading and pressing :key-cap{k="enter"}.

- **⇐ Proposed.** An answer that follows from your vision or from earlier answers is pre-selected and marked ⇐. A confirmed proposal moves straight on. If a new project went through the [vision](/docs/guides/roadmap) first, the advisor proposes an answer for every ground rule the vision states or implies while you review the roadmap, so the questions open with answers waiting.
- **★ Recommended.** When nothing is derived, the advisor's recommendation is marked ★ and pre-selected.
- **✎ Write my own answer.** Typing chooses this.
- **↷ Skip — leave it for later.** Always the first choice, never the pre-selected one. :key-cap{k="tab"} or typing "skip" does the same.

An option has a short name for the list and a complete answer, shown in full under the list for the highlighted option (`picking writes this`). For a broad question, that means every layer and which may depend on which, or each tool with its role. Nothing is written until you pick an option or type your own.

Skipped questions, and those left for later, stay in the Foundation saying *Decide later*. They are not asked again in the same pass, they do not block the first change (the gate lists them as warnings), and every agent reads that they are not settled. A change that depends on one raises it as an open question instead of assuming an answer.

A pass ends once every question is answered or skipped. :key-cap{k="ctrl+f"} (or typing "done") ends it early; what is still open is left for later.

## The advisor

With an AI advisor, setup stays short:

- **It proposes from the domain.** Once you have said what the system is for, it proposes a current, sensible answer for each question marked for it.
- **It asks follow-ups sparingly.** After each answer it looks at what the answer leaves open. At most one question the first change cannot do without is asked next, shown as `✦ follow-up to “…”`. Every other detail it notices is written into the Foundation as *Decide later*. A follow-up raises no follow-ups of its own. While it looks, :key-cap{k="enter"} continues without waiting.
- **It helps when you are unsure.** Press :key-cap{k="?"}, type "help" or "not sure", or press :key-cap{k="enter"} on an empty answer. You get a plain-words explanation, examples for your project, and simpler questions to answer first. Their answers often derive the hard one.

:key-cap{k="ctrl+d"} drops a question the advisor added that is not relevant. Set `SPECTACULAR_NO_ADVISOR=1` to run setup without AI; the intro then says `AI suggestions are off: …`.

### Presets (◇)

Common answers need no waiting. A small table of presets knows what "Python", "TypeScript", "Rust", "Go", "Postgres", "hexagonal" and similar answers mean for the questions still ahead. Their options (uv, poetry or pip; pytest; FastAPI; …) appear the instant you answer, marked ◇. What a preset leaves open, such as the Python version or the Rust edition, is recorded for later, not asked.

The advisor refines preset options in the background (`◇ instant suggestions, AI refining…`), but it never moves the option you have selected or touches a question you already answered. Presets never carry version numbers: those are always looked up.

### Architecture styles derive layer rules

Choose an architecture style and the layers question gets a proposed answer at once (⇐, confirmed with :key-cap{k="enter"}), without a model. For Clean Architecture that is *entities ← use cases ← interface adapters ← frameworks & drivers, dependencies point inward only, an inner layer never imports an outer one*, with folder names, and where business rules and I/O live. Hexagonal (ports and adapters), layered, MVC, modular monolith and vertical slices have their own rules. The advisor then fits them to your project.

## Revising an option with AI

Press :key-cap{k="ctrl+r"} on an option, on the answer already given, or on a draft you typed. It opens the same conversation as [revising a requirement](/docs/guides/reviewing#revising-with-ai): say what should change, see the diff, then accept, ask again, or discard. Only an accepted revision is saved.

## Keys

| Key | Does |
| --- | --- |
| :key-cap{k="↑"} / :key-cap{k="↓"} | Choose an option |
| :key-cap{k="enter"} | Pick, save, skip or keep, depending on the selection |
| :key-cap{k="tab"} | Skip the question |
| :key-cap{k="←"} / :key-cap{k="→"} | Previous / next question (move the cursor while typing) |
| :key-cap{k="?"} | Not sure: explanation, examples, simpler questions |
| :key-cap{k="ctrl+r"} | Revise with AI |
| :key-cap{k="ctrl+e"} | Open the answer in `$EDITOR` |
| :key-cap{k="ctrl+d"} | Drop an advisor-added question as not relevant |
| :key-cap{k="ctrl+f"} | Done; the rest is left for later |
| :key-cap{k="ctrl+c"} | Back |

Answers are saved as you go.

## Where it is stored

::file-tree
---
tree: |
  spec-tacular/
    foundation/
      domain.md
      stack.md
      architecture.md
      conventions.md
notes:
  - { path: foundation/, note: 'read by every agent; commit it' }
  - { path: domain.md, note: 'what it is for, who uses it, core terms' }
---
::

`spec-tacular init` scaffolds these files with every question left as `TBD` on purpose; on a new project, those nobody can answer yet say *Decide later* instead. You can edit them by hand. To see what is still unanswered:

```bash
spec-tacular foundation
```

## Existing or new project

- **New project.** Describe your [vision](/docs/guides/roadmap) first. The ground rules come next and are mostly confirming proposals.
- **Existing project, or a project that skipped the vision.** The ground rules start with the domain question, and the rest is proposed from that.
- **A project that used OpenSpec before spec-tacular.** It has no Foundation yet; pressing :key-cap{k="f"} writes the questions.
