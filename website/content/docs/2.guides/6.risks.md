In OpenSpec, risks are a prose section that nobody accepts or tests. In spec-tacular, each risk is its own item: it is reviewed, the design must answer it by name, and a task must guard it with a test. This page follows a risk from `risks.md` to the hazard register.

## risks.md

Once the specs are accepted, the change lists its risks in `risks.md`: what it could break. The agent is told that every change has at least one: if it truly finds none, it says what it looked at and why nothing there can break, as a single low-severity risk with an `Unmitigated:` line.

Each risk is one block:

```markdown
### Risk: Export leaks other users
- **Hazard:** a user receives data that belongs to another user
- **Affects:** export: Export data
- **Boundary:** an export requested while another user's export runs
- **Causes:** the export query is not scoped to the caller
- **Severity:** high
- **Guard:** every exported row belongs to the caller
- **Check:** a test exports for one user with another user's data present
```

| Field | What it says |
| --- | --- |
| Hazard | What must not happen, as an observable outcome |
| Affects | The requirements and existing capabilities it threatens |
| Boundary | The situation it arises in |
| Causes | Optional: what could bring it about |
| Severity | `high`, `medium` or `low` |
| Guard | The property that rules it out |
| Check | How a test shows the guard holds |

A risk you knowingly leave unmitigated replaces Guard and Check with `- **Unmitigated:** why`. A risk that is the same hazard as an entry in the register names it with `- **Known hazard:** HAZ-0003` (see below).

## Reviewing risks

Risks are reviewed in the same queue as the requirements, after them, one at a time. The keys are the same: :key-cap{k="a"} accepts, :key-cap{k="x"} rejects, :key-cap{k="d"} defers, and :key-cap{k="r"} revises with AI. An edit sends a risk back to pending. A risk without its hazard, guard or check is flagged:

```
  ! missing guard, check — without them this risk cannot be guarded
```

The design cannot be drafted until the risks are accepted. See [Reviewing requirements](/docs/guides/reviewing) for the review loop.

## Following each risk through

After the risks are accepted, each one has to be followed through, and the overview names any that is not:

```
risks: 2/2 accepted
! the design does not answer risk "Export leaks other users"
! guard ticked off without being shown red: "Export leaks other users"
! 1 file changed outside the boundary: lib/oops.ts
```

### The design answers each risk by name

The design must answer every accepted risk by its name. The check is that the name appears in `design.md`, ignoring case and spacing. A name is the cheapest link you can check, and the one an agent is least likely to forget when told to use it. A risk left `Unmitigated:` already carries its reason and needs no answer.

An unanswered risk is a warning, not a block, because a design can answer a risk in words the check misses. It is repeated when the tasks are drafted. The design agent is also told that a risk it cannot mitigate is a reason to stop, the same as contradicting requirements.

### Guard tasks

The tasks carry one guard task per risk, marked `(guard: <risk>)`. Its test must be shown to fail with the mitigation removed: a test that passes either way guards nothing. The agent records how, with `(shown red: …)` on the task:

```markdown
- [x] 3.1 (guard: Export leaks other users) Test that an export holds only the
      caller's rows (shown red: removed the user filter, the test failed)
```

::warning
`(shown red: …)` is a claim the agent records. spec-tacular checks that a ticked guard task carries it, not that the test really failed. A guard ticked off without it still counts as an open task, and the overview names it. For evidence that the guard test passes, set up [verification](/docs/advanced/verification), where tests tagged `[risk:<change>#<slug>]` are run and recorded.
::

Recording `(shown red: …)` does not send the accepted tasks back to be read again. A risk with no guard task at all is named when implementing starts: `no guard task for risk "…"`.

## Unmitigated risks

A risk can be left unmitigated on purpose, with its reason in the `Unmitigated:` line. In a project with [consequence classes](/docs/advanced/consequence-classes), changes in P0 and P1 follow the rule `guard-high-risks`: a high-severity risk cannot be left unmitigated, and the design is refused until it has a guard:

```
a P0 change cannot leave a high-severity risk unmitigated: "Export leaks other users"
```

A class that waives this rule must give a reason, which is shown wherever the rule would have applied. Without a `classes.yaml`, no class rule applies.

## The hazard register

Risks outlive their change. When a change is archived, each accepted risk joins the hazard register in `spec-tacular/hazards/`: one numbered file per hazard, like the ADRs. Each entry holds what must not happen, its causes, what it affects, the controls put in place and the guard tests that verify them.

A later risk of the same hazard names it with `- **Known hazard:** HAZ-0003`, and updates that entry instead of adding a second. Every risks draft starts from the register.

::file-tree
---
tree: |
  spec-tacular/
    hazards/
      0001-export-leaks-other-users.md
notes:
  - { path: hazards/, note: 'one file per hazard; commit it' }
---
::

### Statuses

A hazard's status follows its guards' latest results, which `spec-tacular evidence --run` keeps recording after their change is gone:

::terminal-block
---
title: spec-tacular hazards
lines: |
  $ spec-tacular hazards
  HAZ-0001  open        high     Export leaks other users
             guard failing: [risk:add-export#export-leaks-other-users]
  HAZ-0002  unmitigated low      Huge export
             out of scope until pagination
---
::

| Status | Means |
| --- | --- |
| mitigated | Every guard passed its latest run |
| unverified | A guard was never run, or was waived |
| open | A guard is failing, or no control is verified by a test |
| unmitigated | Left unmitigated, with its reason |
| closed | Its entry's status says `closed`; not listed as due for review |

A hazard whose guard is failing is said on every `--print` overview. `spec-tacular hazards` exits non-zero while any hazard is open or has a guard that was never run, so you can use it in CI; a guard you waived with a reason does not fail it. An entry not looked at for 90 days is listed as due for review. Record a look with:

```bash
spec-tacular hazards --reviewed HAZ-0001
```
