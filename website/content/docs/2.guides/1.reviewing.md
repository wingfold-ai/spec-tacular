title: Reviewing requirements

The review is the screen spec-tacular exists for. It shows a change's requirements, and later its risks, one at a time, and asks you to decide each one. This page covers the keys, what the card shows, how acceptance tracks the text you read, and where your decisions end up.

## Why one at a time

In plain OpenSpec, reviewing means reading a folder of spec files in your editor, and nothing records what you agreed to. spec-tacular gives each requirement an explicit state: `accepted`, `rejected`, `deferred` or `pending`. The next stage waits until every requirement is accepted or deferred. Decisions are saved the moment you make them, and reopening a review resumes where you stopped.

Open the review from the change overview with :key-cap{k="enter"} on **▶ Review**.

## The keys

| Key | Does |
| --- | --- |
| :key-cap{k="a"} | Accept the item |
| :key-cap{k="x"} | Reject it. Asks `Why reject?`; a reason is optional |
| :key-cap{k="d"} | Defer it. Asks `What would verify it?`; a reason is required |
| :key-cap{k="r"} | Revise it with AI (see below) |
| :key-cap{k="ctrl+e"} or :key-cap{k="E"} | Open it in `$EDITOR` |
| :key-cap{k="y"} | Copy it to the clipboard |
| :key-cap{k="s"} | Skip it for now |
| :key-cap{k="n"} / :key-cap{k="p"}, :key-cap{k="↓"} / :key-cap{k="↑"} | Next / previous item |
| :key-cap{k="m"} | Mark a flagged value as an example (when flags are shown) |
| :key-cap{k="pgdn"} / :key-cap{k="pgup"} | Scroll a card taller than the screen |
| :key-cap{k="?"} | Show every key; any key closes it |
| :key-cap{k="q"} | Back to the overview |

A deferral needs a reason because a deferred requirement leaves the change without being verified. The reason goes into the pending-validation register, so it is still visible after the change is archived. Press :key-cap{k="ctrl+c"} to cancel a reason prompt.

## What the card shows

The top line says where you are, for example `export   requirement 3 of 12   [ADDED]`. Below it come the requirement's text and each of its scenarios. Then come any flags. Flags are advisory: none of them blocks a stage.

- **Happy path only.** When no scenario says what must not happen, the card shows `! no scenario says what must not happen, or how it fails — a negative test needs one`.
- **Vague words.** A requirement without a formal form is flagged for words it leaves undefined, such as *promptly*, *large* or *gracefully*: `! undefined words: … — how much, how soon, compared to what?`
- **Premature specificity.** A requirement that names an endpoint, a table, a field, a class or a file it has not earned gets a numbered list of questions, such as `names an HTTP endpoint: POST /v1/export`. More than three fold behind :key-cap{k="f"}.
- **Missing risk fields.** A risk without its hazard, guard or check shows `! missing … — without them this risk cannot be guarded`.

### Marking a value as an example

Sometimes a specific value belongs in a requirement as an illustration, not as a promise. Press :key-cap{k="m"}, then the flag's number (`Mark which as an example? 1-3 · any other key cancels`). The value is rewritten as `{{example: ...}}` in the spec. The card then lists it under `examples, not contracts:` instead of flagging it:

```
 The system SHALL let a user export their data in a portable format CSV,
 exposed as POST /v1/export and persisted to the user_exports table by
 `ExportController`.

   examples, not contracts: CSV

   1. names an HTTP endpoint: POST /v1/export
   2. names a field or table: user_exports
   3. names a class or symbol: ExportController
```

You pick a flag by number on purpose: with several on one requirement, picking the wrong one would rewrite the spec.

A requirement with a formal form also shows the formula read back in plain words, its open questions and its test matrix. See [Formal requirements](/docs/advanced/formal-requirements).

## Revising with AI

Press :key-cap{k="r"} to change a requirement by talking to the agent instead of editing Markdown. The panel shows the requirement as it is now and asks `How should this requirement change?`.

::steps
### Say what should change
Type a request, for example "make the timeout configurable" or "split it into two scenarios". :key-cap{k="alt+enter"} or a trailing `\` adds a new line. :key-cap{k="enter"} sends it.

### Read the diff
The agent answers with the revised requirement, shown as a diff against the file. If the revision needs new glossary entries, they are listed above the diff.

### Decide
:key-cap{k="a"} writes it. :key-cap{k="r"} asks for more changes; the agent sees every earlier request and proposal, and you can go as many rounds as you like. :key-cap{k="q"} discards it.
::

Nothing is written before :key-cap{k="a"}. Accepting replaces only that requirement's block; every other byte of the file stays as it was. Pressing :key-cap{k="ctrl+c"} while the agent works leaves the file untouched.

A revised requirement goes back to pending, with the cursor on it, so you accept its new text: `Revised and written — it is pending again: a accepts the new text`. Other requirements keep their decisions, even when the revision renamed one. When you revise a rejected requirement, the prompt starts from your rejection reason.

Risks are revised the same way. Ground rules, design decisions and harness bindings are not; for those, :key-cap{k="E"} opens your editor.

::note
Revising needs an agent. With `SPECTACULAR_NO_ADVISOR=1`, or when no agent is available, the panel says `No AI to revise with: …`; any key closes it, and :key-cap{k="E"} opens the requirement in your editor instead.
::

## Acceptance holds for the text you read

An acceptance is tied to the exact text you read. Each item is hashed when you decide it. If the file changes afterwards, through your editor, a redraft or a revision, the item shows:

```
  ! changed since you marked it accepted — review it again
```

The stage is no longer complete, and the stage after it is blocked again until you review the item. The same applies to documents accepted as a whole, such as the proposal: after an edit, the overview says `The proposal changed since you accepted it. Read it again, then accept it or ask for changes.` Ticking tasks off while implementing does not count as a change.

## Progress and the review record

The bottom line of the review always shows progress, for example `17 accepted · 3 rejected · 2 deferred · 4 pending`. When you leave with :key-cap{k="q"}, the overview's pipeline bar updates to match.

Every change also carries `openspec/changes/<id>/review.md`. It is rewritten from the review state on every decision and once more before archiving. It lists:

- what was accepted, with the answers to formal-form questions;
- what was rejected, and why;
- what was deferred, and what it waits for;
- what is not decided yet;
- anything allowed or waived.

Because it sits in the change folder, `openspec archive` moves it with the change, and it reads the same without spec-tacular. Do not edit it by hand: your edits are overwritten.

::file-tree
---
tree: |
  openspec/
    changes/
      add-export/
        review.md
  .spec-tacular/
    review/
notes:
  - { path: review.md, note: 'what you decided, readable in git; rewritten on every decision' }
  - { path: review/, note: 'the review state it is written from; committed' }
---
::

## When the agent stops

An agent does not design around accepted requirements that contradict each other or leave a decision open. It stops and writes a report instead of the artifact. The overview shows `⚠ The agent stopped instead of writing the design: …`, and **▶ Why it stopped** opens the report. Each conflict or gap is listed with the full text of every requirement involved, so you can see the contradiction yourself.

The report offers these buttons:

| Key | Button |
| --- | --- |
| :key-cap{k="s"} | **▶ Revise them in the review**: opens the review on the first requirement named |
| :key-cap{k="b"} | **↩ Fix the …**: the agent redrafts what this artifact was drafted against (for a design, the risks) with the report and your answer |
| :key-cap{k="w"} | **↻ Draft the … again**: asks for your answer to what it raised; leave it empty to try again as it is |
| :key-cap{k="ctrl+e"} | **✎ Write it myself** |

Fixing the requirements comes first because that is usually where the problem is. Until the next draft, the overview keeps the warning up, and :key-cap{k="o"} reopens the report.
