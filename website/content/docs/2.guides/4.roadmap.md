A new project starts from its vision rather than a change: there is nothing to change yet. You describe what you are building, an AI interviews you, and the result is split into a roadmap of slices, each one a change of its own. This page covers the interview, reshaping the slices, and how slices are specified ahead of being built.

## Why a roadmap

Asking an agent to plan a whole new app at once tends to produce many changes proposed together, too many to review. The roadmap sequences the idea instead. One slice is specified at a time, so the review queue never holds more than a single change.

The vision also comes first because it is the one thing only you know. Most of the [ground rules](/docs/guides/foundation) follow from it, so they are proposed from it afterwards.

## Describe your vision

On the start screen of a new project, choose **Describe your vision**. Say what you are building, and for whom, in your own words; a few sentences is enough. If you already answered the domain question of the ground rules, the description starts from that answer, so nothing is described twice: add to it or press :key-cap{k="enter"}.

If the project is not new after all, press :key-cap{k="ctrl+n"} (**not a new project**). You then go to the ground rules, domain first, and your first change.

## The interview

The AI restates what it understood and asks one question at a time, with options. It is told to ask at least one question, however complete the description.

| Key | Does |
| --- | --- |
| :key-cap{k="↑"} / :key-cap{k="↓"} | Choose an option |
| :key-cap{k="enter"} | Answer |
| :key-cap{k="tab"} | Skip the question (so does Skip, the first choice, or typing "skip") |
| :key-cap{k="ctrl+r"} | Revise the highlighted option or your draft with AI |
| :key-cap{k="ctrl+d"} | That's enough: make the slices |
| :key-cap{k="ctrl+c"} | Back |

The interview ends when the AI has enough, when you say "done", or after twelve questions.

## Reshape the slices

The AI then proposes three to eight slices in build order. The first is the smallest thing a user can do end to end. The selected slice is shown in full. Nothing is written until you confirm, so reshape them first:

| Key | Does |
| --- | --- |
| :key-cap{k="↑"} / :key-cap{k="↓"} | Select a slice |
| :key-cap{k="space"} | Keep or drop it |
| :key-cap{k="m"} | Merge it with the next one into one change |
| :key-cap{k="shift+↑"} / :key-cap{k="shift+↓"} | Move it |
| :key-cap{k="e"} | Reword it, as *Title — what it does* on one line |
| :key-cap{k="enter"} | Create the roadmap |

A slice never moves before one it builds on; trying says, for example, `“Share a list” builds on “Create a list”, so it has to come after it`. The last slice has nothing after it to merge with. At least one slice must be kept.

## What is written

::file-tree
---
tree: |
  spec-tacular/
    vision.md
    roadmap.yaml
notes:
  - { path: vision.md, note: 'the vision and the interview; every agent reads it' }
  - { path: roadmap.yaml, note: 'the vision and the ordered list of slices' }
---
::

The first slice becomes your first change. The ground rules come next, proposed from the vision. The first change's proposal is drafted once they are settled.

To see the roadmap from the shell:

```bash
spec-tacular roadmap
```

It prints the vision and each slice with its summary and what it comes after. `spec-tacular roadmap --promote <slice>` makes a slice active, and `spec-tacular roadmap --done <slice>` marks one finished.

## Specifying ahead

You do not have to wait for a slice to be built before specifying the next one. Once a slice's proposal and specs are accepted, the next slice can be specified. The overview shows `s  specify the next slice on the roadmap: <slice>`; press :key-cap{k="s"} to start it.

It need not be the next in line. Slices without a change are listed after the changes in the overview. Select one with :key-cap{k="↓"} (or a click) to read its summary and what it depends on. **▶ Start this slice** (:key-cap{k="s"}) starts it, or the overview says why it cannot start yet, such as a dependency that is not specified.

Starting a slice says:

```
Started <slice>: specify it now — its design waits until the slices before it are applied.
```

## What waits for earlier slices

A slice's proposal and specs say *what* it does, and can be written early. Its design, tasks and implementation say *how* it is built on the code of the slices before it, so they wait until those slices are applied. The overview says, for example, `Specified. The design waits until create-list is applied — it builds on that code.`

Applied means every task is ticked off, except tasks marked `(defer: …)` that need a deployment to verify. An applied slice turns ✓ on its own.
