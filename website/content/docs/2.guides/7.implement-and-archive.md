Once the tasks are accepted, planning is done and the change is implemented by your agent, in its own session. This page covers how that session is opened, what spec-tacular checks while it runs, work that needs a deployed environment, and archiving.

## Opening the agent

The overview's next step says `Planning is done. Implement it — the agent opens right here, as if you had started it yourself.` Press :key-cap{k="w"} on **▶ Implement it in Claude Code** (or opencode, with `--driver opencode`).

spec-tacular opens the agent on the change's apply instructions in a new tab of your terminal:

| Terminal | Opens |
| --- | --- |
| tmux | a new tmux window |
| kitty | a new kitty tab |
| WezTerm | a new WezTerm tab |
| GNOME Terminal | a new GNOME Terminal tab |
| Konsole | a new Konsole tab |
| iTerm | a new iTerm tab |

In a terminal that cannot open tabs, such as an IDE's, it opens a new window of the desktop's terminal instead. Only when no tab or window can be opened does the agent take over spec-tacular's own terminal until it exits.

The session is exactly as if you had started it yourself, in your own permission mode (auto, accept edits, or ask). There is one addition: some commands never ask for approval:

- the project's test commands, from `spec-tacular/verification.yaml`;
- its typechecker and linter;
- spec-tacular's own checks;
- OpenSpec's read-only commands;
- the commands output is read through, such as `grep` and `head`.

Because routine checks do not ask, what the agent does ask about is worth reading. The agent is also told to write files with its edit tools, to run checks as plain commands, and to use the toolchain that is installed.

## Following the tasks

spec-tacular stays open and shows the change being implemented:

```
◉ Being implemented in another tab — 3 of 8 tasks ticked off so far
```

It follows the tasks as the agent ticks them off. If you come back to a change that is partly done, the next step says `3 of 8 tasks ticked off. Carry on implementing — the agent opens right here.`

A guard task counts as done only once it also records `(shown red: …)`. See [Risks and guards](/docs/guides/risks#guard-tasks).

## The boundary

The proposal names a `## Boundary`: the paths the change expects to touch, in backticks. Once implementing has started, files changed outside it are listed on the change:

```
! 1 file changed outside the boundary: lib/oops.ts
```

"Changed" means changed on the branch: committed since it left the default branch, plus uncommitted and untracked files. Files under `openspec/`, `spec-tacular/` and `.spec-tacular/` never count, since writing those is part of every change, and neither do the test files spec-tacular generates.

::note
The boundary is advisory. Files outside it are flagged, not blocked. A change can have a good reason to reach further than it planned, and only a person can tell whether it was right.
::

## Work that needs a deployment

Some work cannot be verified without a running deployed environment. It should not block the change.

- **Tasks.** A task that needs a deployment is marked `(defer: …)`, for example `- [ ] 4.2 (defer: awaiting-deployment) Verify export completes against a deployed instance`. The agent skips it, and it does not count as open. The schema tells the agent to use this only for work that really needs a deployment, not for work that is merely hard.
- **Requirements.** In the review, defer a requirement with :key-cap{k="d"} and say what would verify it.

A change is applied once every task is ticked off or deferred: `Implemented: all 7 tasks are ticked off. 1 deferred until it is deployed — they are checked when it is archived.`

## Reading the diff (P0)

In a project with [consequence classes](/docs/advanced/consequence-classes), a P0 change has one more step under the rule `diff-review`. The agent wrote the code, so it cannot be the one to certify it. After the last task is ticked off, the next step says `All tasks are ticked off. This is a P0 change: read the code the agent wrote, then accept it.`

Open the implementation diff with **▶ Read the implementation** (:key-cap{k="enter"}) on the overview, read it, and accept it with :key-cap{k="a"}. From the shell:

```bash
spec-tacular diff add-export
spec-tacular diff add-export --accept
```

Like every acceptance, it holds for that text: a later change to the code sends it back. Archiving is refused until it is accepted.

## Archiving

When every task is ticked off or deferred, the overview offers **▶ Archive it** (:key-cap{k="A"}). It first shows what archiving would do, or why the change may not be archived yet. :key-cap{k="enter"} archives it: the accepted requirements become the baseline in `openspec/specs/`, and its risks join the [hazard register](/docs/guides/risks#the-hazard-register).

From the shell, `--dry-run` shows the same plan without archiving:

::terminal-block
---
title: spec-tacular archive
lines: |
  $ spec-tacular archive add-export --dry-run
  1 requirement(s) merge into the baseline
  1 divert to pending validation
    data-export: Export completes against a deployment — a deployed instance to run against

  Dry run — nothing written.
---
::

Archiving is refused when:

- a requirement is neither accepted nor deferred (`Archiving now would merge text nobody agreed to`);
- the change is P0 and nobody has accepted its implementation diff;
- with `spec-tacular/verification.yaml` in place, an accepted requirement or risk is not passing or excepted (see [Verification](/docs/advanced/verification)).

Before archiving, `review.md` is written once more, so `openspec archive` moves your review decisions with the change.

## The pending-validation register

Deferred requirements do not merge into the baseline. They wait in `spec-tacular/pending-validation.md` with what would verify them, so what was never verified stays visible and out of the accepted specs.

```bash
spec-tacular pending
```

Once a deferred requirement is verified, for example after deployment, move it into the baseline:

::terminal-block
---
title: spec-tacular verify
lines: |
  $ spec-tacular verify data-export --requirement "Export completes against a deployment"
  Verified 'Export completes against a deployment' into <project>/openspec/specs/data-export/spec.md
  Specification 'data-export' is valid
---
::

This is the one place spec-tacular writes to `openspec/specs/` itself, and it runs `openspec validate` afterwards.
