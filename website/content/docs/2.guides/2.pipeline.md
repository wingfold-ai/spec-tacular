---

Every change moves through the same stages in a fixed order, and each stage waits until a person has accepted the one before it. This page covers the stages, how each is accepted, drafting with an agent, the job pane, and the change overview.

## The stages

```
proposal → specs → risks → design → tasks → implement → archive
```

`spec-tacular init` installs the `spec-tacular` schema, which makes this order strict. OpenSpec's own `spec-driven` schema lets `design` follow the `proposal` alone, so the design can be written before anyone has agreed on the specs. Under spec-tacular's schema, `design` requires accepted specs and risks, and `tasks` requires specs, risks and design.

| Stage | What it is | How it is accepted |
| --- | --- | --- |
| proposal | Why the change, what it changes, and its `## Boundary` | As a whole |
| specs | The requirements and their scenarios | Requirement by requirement, in the review |
| risks | What the change could break, in `risks.md` | Risk by risk, in the same review |
| design | How to build it, answering every risk by name | As a whole |
| tasks | The plan, including a guard task per risk | As a whole |
| implement | Your agent works through the tasks | When every task is ticked off or deferred (in a P0 change, also once you accept the implementation diff) |
| archive | Accepted requirements become the baseline | Confirmed with :key-cap{k="enter"} |

A stage is only ticked off once it is accepted. A file that exists is `written`, not `accepted`: absence of review is never treated as review. An acceptance holds for the text you read, so editing or redrafting a document sends it back to be read again (see [Reviewing](/docs/guides/reviewing#acceptance-holds-for-the-text-you-read)).

### Reading a document

The proposal, design and tasks open as documents. Scroll with :key-cap{k="↑"} / :key-cap{k="↓"} or :key-cap{k="space"}, then pick a button:

- **✓ Accept it** (:key-cap{k="a"}) accepts it.
- **↻ Redraft with feedback** (:key-cap{k="r"}) asks `What should change? The agent redrafts it with this.`
- **✎ Edit it** (:key-cap{k="ctrl+e"}) opens it in `$EDITOR`.
- **← Back** (:key-cap{k="q"}).

Accepting starts nothing by itself. The notice says what comes next, for example `✓ The proposal of add-export is accepted — w drafts the specs`. :key-cap{k="v"} on the overview reads the latest artifact again later.

## The change overview

Select a change in the list with :key-cap{k="↑"} / :key-cap{k="↓"}. Its panel shows the pipeline bar, any warnings, and a **Next** section: one sentence on what to do, and the next steps as buttons. :key-cap{k="enter"} presses the focused button; :key-cap{k="←"} / :key-cap{k="→"} or :key-cap{k="tab"} move between them.

| Button | Key | When |
| --- | --- | --- |
| **▶ Review** | :key-cap{k="enter"} | Requirements or risks are waiting |
| **▶ Read the …** | :key-cap{k="enter"} | A document is waiting to be accepted |
| **✦ Let an agent draft it** | :key-cap{k="w"} | The next artifact can be drafted |
| **✎ Write it myself** | :key-cap{k="ctrl+e"} | Same, but you write it in `$EDITOR` |
| **▶ Implement it in Claude Code** | :key-cap{k="w"} | Planning is done |
| **▶ Archive it** | :key-cap{k="A"} | Every task is ticked off or deferred |
| **▶ Why it stopped** | :key-cap{k="enter"} | The last draft stopped with a report |

Other overview keys: :key-cap{k="n"} starts a new change, :key-cap{k="b"} reports a defect, :key-cap{k="f"} opens the ground rules, :key-cap{k="ctrl+j"} opens the jobs, :key-cap{k="?"} shows help and :key-cap{k="q"} quits.

Warnings stay on the change until they are dealt with, for example:

```
! the design does not answer risk "Export leaks other users"
! guard ticked off without being shown red: "Export leaks other users"
! 1 file changed outside the boundary: lib/oops.ts
```

## Drafting in the background

Press :key-cap{k="w"} to have an agent draft the next artifact. It runs in the background, so you can keep reviewing another change while it works. Its progress streams into the change panel (`Claude Code is drafting the design · …`), and the draft opens for you to read when it lands.

Only one agent works on a change at a time. Pressing :key-cap{k="w"} again says `An agent is already working on add-export — ctrl+j to watch it`.

With Claude Code, drafting agents run as `claude -p` with `--permission-mode acceptEdits` and read-only `openspec` commands allowed. Nobody is there to approve a tool call, so without that every write would be denied. To allow more, add flags with `SPECTACULAR_CLAUDE_ARGS` (see [Configuration](/docs/reference/configuration)).

### The job pane

Press :key-cap{k="ctrl+j"} from the overview, including in the middle of a review, to see every job: what each agent read, ran and wrote, and every tool call it was refused. Your place in the review is kept.

| Key | Does |
| --- | --- |
| :key-cap{k="j"} / :key-cap{k="k"} | Select another job |
| :key-cap{k="x"} | Cancel the selected running job (asks first: `Its work in progress is lost.`) |
| :key-cap{k="q"} | Close the pane |

### From the shell

The same dispatch is a command. It returns immediately:

```bash
spec-tacular run design -c add-export
spec-tacular jobs                        # list jobs
spec-tacular jobs --job <id>             # tail one job's output
spec-tacular jobs --job <id> --cancel    # stop a running job
```

`spec-tacular run` prints the job's id and log path, and `Follow it with: spec-tacular jobs --job <id>`. `spec-tacular instructions <artifact> -c <change>` prints the prompt an agent would get, if you want to draft with your own tooling.

## Refused while unreviewed

Both commands go through the same gate as the TUI. Asking for the design while requirements are still pending is refused with exit code 1, naming what blocks it:

```
Refused: design is not ready to be written
  - specs: 3 pending of 12 requirements
```

The message ends with how to review it in the TUI. A prerequisite that changed after acceptance is printed as a warning either way. The gate also refuses a design whose formal forms cannot be read or contradict each other, and, in P0 and P1 changes, a high-severity risk left `Unmitigated:`.

## The usage sidebar

A sidebar shows which driver and model is answering, what it has cost, and what it is doing right now. It appears once the terminal is at least 130 columns wide. :key-cap{k="ctrl+b"} expands it into a breakdown per model and per job; on a narrower terminal it opens full width.

Cost and tokens come from the agents themselves: Claude reports actual USD, opencode its own cost. The total is kept in `.spec-tacular/usage.jsonl`, so a restart does not reset it. Claude Code reports no cost for the interactive implementing session, so its tokens are read from its transcript and shown as `+ implementing`; run `/cost` in that session for its cost.
