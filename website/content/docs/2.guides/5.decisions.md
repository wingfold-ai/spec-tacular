---
title: Decisions and ADRs
description: "Mark a design decision global, promote it with p to a numbered ADR, and every later change gets it as a rule."
---

A design records its decisions with their rationale. Most apply to one change. Some are architectural, such as the error model or the persistence choice, and belong to the whole project. This page covers how to mark those, promote them to architectural decision records (ADRs), and how agents use them afterwards.

## Why promote decisions

OpenSpec has no project-level decision record. A decision made in one change's `design.md` stays in that change, so the next change's design decides the same question again, possibly differently. Promoting it to an ADR makes it a rule that every later design has to follow, or explicitly supersede.

## Marking a decision's scope

A design has a `## Decisions` section with one `###` heading per decision. The design agent marks each one with its scope:

```markdown
## Decisions

### Errors are values

**Scope: global**

Functions that can fail return a result instead of throwing. ...
```

- `**Scope: local**` applies to this change only.
- `**Scope: global**` is an architectural rule the whole project should follow.

An unmarked decision counts as local: promoting something project-wide without anyone saying so would be the more damaging guess. To change a scope, edit the marker in `design.md`.

## Promoting with p

Design decisions appear in the change's review queue after the requirements and risks. A decision marked global shows:

```
  this decision is marked global — p promotes it to a project-wide ADR
```

Press :key-cap{k="p"}. spec-tacular writes the next numbered ADR and the notice says `promoted to ADR-0001`. On any other item, :key-cap{k="p"} still means *previous*.

Promoting does two things:

1. It writes `spec-tacular/decisions/NNNN-slug.md`, with the decision's name as its title, `**Status:** accepted`, the date, and the change it came from. The scope marker is dropped, since an ADR is global by definition.
2. It replaces the decision's body in `design.md` with a reference, such as ``See ADR-0001 (`spec-tacular/decisions/0001-errors-are-values.md`).``

Because promoting rewrites `design.md`, the decision's text has changed, and you accept it again like any other edit.

::file-tree
---
tree: |
  spec-tacular/
    decisions/
      0001-errors-are-values.md
      0002-postgres-for-persistence.md
notes:
  - { path: decisions/, note: 'project-wide ADRs; commit them' }
---
::

## Listing ADRs

```bash
spec-tacular adr
```

::terminal-block
---
title: spec-tacular adr
lines: |
  $ spec-tacular adr
  ADR-0001  accepted                   Errors are values
---
::

With no ADRs yet, it says `No architectural decisions recorded yet.` and `Promote one while reviewing a design: press p on a decision.`

## How agents use ADRs

Every agent that drafts an artifact gets the accepted ADRs in its context, under `# Accepted architectural decisions`, next to the [ground rules](/docs/guides/foundation). The design agent is told to read `spec-tacular/foundation/` and every accepted ADR first, and that the design must conform to them. Where it cannot, it has to propose superseding the specific ADR by number, with its rationale, and never diverge silently.

Only accepted ADRs bind. An ADR whose status line reads `**Status:** superseded by ADR-0003` is listed as superseded by `spec-tacular adr` and is no longer given to agents. Feeding a reversed decision to an agent as a rule would bring it back.

::tip
The design agent is told to mark a decision global only when a later change must follow it (layering, error handling, persistence, authentication, API style, a dependency), and only once: a rule the ground rules or an accepted ADR already state is not decided again. How the change's own code is shaped stays local.
::
