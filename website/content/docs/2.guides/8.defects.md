Fixing something is a change of its own kind. A defect change has its own schema, with the same stage names as a normal change, so every review, gate and evidence rule applies. This page covers how to start one, the report's first decision, and how the fix is verified.

## Why a separate kind of change

Most defects trace back to a requirement that allowed what happened, not only to code. If you fix the code and leave the requirement as it is, the next change can bring the defect back. So a defect change decides first whose bug it is, and its specs follow from that answer.

## Reporting a defect

In the TUI, press :key-cap{k="b"} on the overview (**report a defect**). It asks:

```
What went wrong? What you saw, what you expected, and how to make it happen — the defect report starts from this.
```

Then you name the change, as for any other change. From the shell:

```bash
spec-tacular defect export-leak --description "An export included another user's rows"
```

::terminal-block
---
title: spec-tacular defect
lines: |
  $ spec-tacular defect export-leak --description "…"
  Created export-leak, a defect change. Its report decides first whose bug it is —
  the code's, the requirement's, or a gap — and its first task is a reproducer
  that fails on the code as it is.
---
::

The defect schema is installed by `spec-tacular init`, next to the main one. If a project's schemas predate it, the command says `The defect schema is not installed here. Run spec-tacular init --force first.`

## The stages

The stages keep their names, but each has a defect-specific job:

| Stage | In a defect change |
| --- | --- |
| proposal | The report: what went wrong, and whose bug it is |
| specs | The requirement the fix is measured against |
| risks | The defect itself, guarded by the reproducer |
| design | The fix: causes, and why the tests did not catch it |
| tasks | The reproducer first, then the fix |

## The report: whose bug

The report has these sections: Observed, Expected, Reproduce, Whose bug, Violated requirement and Boundary. The most important line is the one that says whose bug it is:

```markdown
## Whose bug
**Whose bug:** requirement

## Violated requirement
**Violated requirement:** export#export-data
```

| Answer | Means |
| --- | --- |
| `code` | The requirement, read literally, rules out what was observed. The requirement was right; the code is wrong |
| `requirement` | The requirement allows what was observed, or can be read to: it is ambiguous, or says the wrong thing |
| `gap` | No requirement covers the behaviour at all |

The drafting agent is told not to settle for `code` just because the fix is in code, and to check the hazard register in case the defect is a known hazard coming back. The report contains no fix yet: that is the design's job.

## Specs follow from the answer

- **Code bug.** The spec repeats the violated requirement unchanged, for you to confirm it was right.
- **Requirement bug.** The spec corrects the requirement.
- **Gap.** The spec adds the missing requirement, with a scenario that is the defect.

The overview flags a change that does not fit its own report:

| Warning | When |
| --- | --- |
| `the report does not say whose bug it is: **Whose bug:** code, requirement or gap` | The line is missing |
| `a code bug changes no requirement, but this one changes "Export data" — is it a requirement bug?` | A code bug whose specs change a requirement |
| `a requirement bug changes a requirement, but the specs only repeat the accepted ones` | A requirement bug (or gap: `a gap adds a requirement, …`) with nothing new to measure the fix against |
| `the report names export#export-data as violated, but the specs do not include it` | A code bug whose named requirement is missing from the specs |
| `no reproducer: the first task is a guard task whose test fails on the unfixed code` | The tasks have no guard task |

## The reproducer is shown red first

The risks start with the defect itself, and its guard is the reproducer: a test that fails on the code as it is. The tasks begin with that test, before the fix:

```markdown
## 1. Reproduce

- [ ] 1.1 (guard: Export leaks other users) Reproducer: a test tagged
      [req:…] [risk:…] that fails on the code as it is

## 2. Fix

- [ ] 2.1 The fix, including how to verify it
```

A test written after the fix may pass either way, and then it proves nothing about the defect. Like any guard task, the reproducer counts as done only once the agent records `(shown red: …)` on it.

::warning
`(shown red: …)` is the agent's record of having seen the test fail. spec-tacular checks that it is there, not that the test failed. With [verification](/docs/advanced/verification) set up, tagged tests are run and their results recorded as evidence.
::

## The fix and the archive

The design (the fix) names the proximate cause, the root cause and the contributing factors, and why the tests did not catch it.

When the defect change is archived, the defect joins the [hazard register](/docs/guides/risks#the-hazard-register), or updates the hazard it is a recurrence of. `spec-tacular evidence --run` keeps recording its guard's results after the change is gone, so if the defect comes back, `spec-tacular hazards` shows the hazard as open again.
