In this guide you start from an empty folder. You describe what you are building, answer a short AI interview, shape the result into a roadmap of small slices, and confirm the ground rules proposed from your vision. Then the first slice goes through the pipeline as your first change.

You need spec-tacular, the OpenSpec CLI and Claude Code (or opencode) installed. See [Installation](/docs/getting-started/installation). If your project already has OpenSpec specs, follow the [Quickstart](/docs/getting-started/quickstart) instead.

## Why the vision comes first

A new project has nothing to change yet. What it is, and for whom, is the one thing only you know, and most of the ground rules follow from it. So spec-tacular asks for the vision first and proposes the ground rules from it. Without a vision, the ground rules would start cold from the domain question.

spec-tacular treats a project as new when `openspec/specs/` holds no specs and nothing is archived.

## 1. Create the folder and run openspec init

```bash
mkdir my-app && cd my-app
openspec init
```

When `openspec init` asks which tools to set up, choose **Claude Code** (or **opencode**).

## 2. Open spec-tacular and set up

::code-group
```bash [Claude Code]
spec-tacular
```
```bash [opencode]
spec-tacular --driver opencode
```
::

The start screen says `OpenSpec is here; spec-tacular is not set up yet.` Press :key-cap{k="enter"} on **▶ Start**. A spinner says `Setting up the project…`. Setup installs the spec-tacular schema and the ground rules files, then opens the vision.

**You should now see** the vision screen, with a stepper at the top: `✓ Set up  ──  2. Vision  ──  3. Ground rules  ──  4. First change`.

## 3. Describe your vision

The panel **Your vision** asks what you are building:

::terminal-block
---
title: vision screen (trimmed)
lines: |
  What are you building?

  This is a new project, so there is nothing to change yet — start from what you
  want it to be. Describe it freely: who it is for, what they will do with it, what
  matters most. Rough is fine; paste a longer text if you have one.

  ✦ Then an AI asks a few questions to sharpen it — skip any, or stop whenever you
    like — and splits it into small slices, each becoming one change.

  › ▏e.g. A booking tool for small clinics: receptionists see free rooms and book them for patients…

  ▶ Continue    Not a new project — just start a change

  enter continue  ctrl+n not a new project  ctrl+c back
---
::

Type your description, or paste a longer text with :key-cap{k="ctrl+v"}. Write at least a few sentences, then press :key-cap{k="enter"}.

::tip
Not a new project after all? Press **Not a new project — just start a change** (:key-cap{k="ctrl+n"}). You go straight to the ground rules, domain first.
::

## 4. Answer the interview

The AI restates what it understood, in a panel titled **What I understood so far**, and asks one question at a time, with options. It asks at least one question, however complete your description is.

| To | Do |
| --- | --- |
| Pick an option | :key-cap{k="↑"} :key-cap{k="↓"}, then :key-cap{k="enter"}. ★ marks the recommended one. |
| Answer in your own words | Type, then :key-cap{k="enter"}. |
| Adjust an option with AI | :key-cap{k="ctrl+r"} on it. |
| Skip a question | **↷ Skip this question**, :key-cap{k="tab"}, or type `skip`. |
| End the interview | **That's enough — make the slices**, :key-cap{k="ctrl+d"}, or type `done`. |

While the AI thinks, a spinner says what it is doing. When the interview ends, it says `Wrapping up…`, then `Splitting your vision into slices — the first is the smallest thing a user can do end to end…`. Meanwhile, in the background, the advisor starts proposing an answer for every ground rule your vision states or implies.

If a request fails, the screen shows `The AI could not continue:` and the reason. Press :key-cap{k="enter"} to ask again.

**You should now see** the roadmap screen.

## 5. Shape the roadmap

The screen **Your roadmap — review the slices** lists 3–8 slices in build order. The first is the smallest thing a user can do end to end. The selected slice is shown in full; the others take a line each. Each slice becomes one change that you review before the next.

Reshape them before anything is written:

| Key | Does |
| --- | --- |
| :key-cap{k="↑"} :key-cap{k="↓"} | Select a slice. |
| :key-cap{k="space"} | Keep or drop it. A dropped slice shows `[ ]`. |
| :key-cap{k="m"} | Merge it with the next one into one change. |
| :key-cap{k="shift+↑"} :key-cap{k="shift+↓"} | Move it. A slice never moves before one it builds on. |
| :key-cap{k="e"} | Reword it, as *Title — what it does* on one line. :key-cap{k="enter"} saves, :key-cap{k="esc"} leaves it as it was. |
| :key-cap{k="enter"} | Create the roadmap. |

The button names the slice you start with: **▶ Create the roadmap — start with “…”**. Press :key-cap{k="enter"}.

spec-tacular writes the slices to `spec-tacular/roadmap.yaml` and the vision and interview to `spec-tacular/vision.md`, which every agent reads. The first slice becomes your first change.

## 6. Confirm the ground rules

The ground rules open next. The notice starts with `Roadmap saved:` and the number of slices. If the proposals are still coming, a spinner says `Proposing answers from your vision — each appears as ⇐ on its question`. When they are ready, the notice says `✦ N ground rules proposed from your vision — ⇐, enter confirms`. Press :key-cap{k="enter"} on **▶ Begin**.

A project that already has specs in `openspec/specs/` or an archived change is asked [all nineteen questions](/docs/getting-started/quickstart#_4-settle-the-ground-rules). On a new project, with neither, only what can be answered on day one is asked:

| | Questions |
| --- | --- |
| Asked | What the system is for, and who uses it |
| Proposed from the vision | the core terms · language and runtime · framework · datastore · package manager and tools · architecture style · layers and which may depend on which · where business rules live · naming · what a test must cover |
| Left for later | domain invariants · out of scope · what is ruled out · error handling · configuration and secrets · code review · comment style · what newcomers get wrong |

::steps
### Confirm a proposed answer

A proposed answer is marked ⇐ and already selected. The box under the list shows in full what picking it writes. Press :key-cap{k="enter"} to confirm it and move on.

### Choose something else

Pick another option with :key-cap{k="↑"} :key-cap{k="↓"} and :key-cap{k="enter"}, type your own answer, or press :key-cap{k="ctrl+r"} to adjust the highlighted option with AI.

### Leave it open

Skip any question with **↷ Skip — leave it for later** or :key-cap{k="tab"}. Press :key-cap{k="ctrl+f"} to finish early and leave the rest for later. That is also the fastest path: confirm the ⇐ answers with :key-cap{k="enter"}, then :key-cap{k="ctrl+f"}.
::

Questions left for later stay in `spec-tacular/foundation/` marked *Decide later*. They are not asked, they do not block the first change, and every agent reads that they are not settled. A change that depends on one raises it then. More in [Ground rules (Foundation)](/docs/guides/foundation).

When you finish, press :key-cap{k="enter"} on **▶ Continue**.

**You should now see** the overview: the main screen, with the **Changes** list on the left and the change panel for the first slice on the right. Under **Roadmap** in the list, each slice has a mark: ◉ for the one being worked on, ○ for planned, ✓ for done.

## 7. Take the first slice through the pipeline

The first slice is a change like any other. Its next step reads *Write the proposal: why this change, and what it changes.* The pipeline bar shows `◉ proposal ── ○ specs ── ○ risks ── ○ design ── ○ tasks ── ○ apply`. Press :key-cap{k="w"} to let an agent draft it. Then go through the stages as in the Quickstart:

1. [Accept the proposal](/docs/getting-started/quickstart#_6-draft-and-accept-the-proposal).
2. [Review the specs](/docs/getting-started/quickstart#_7-review-the-specs-one-requirement-at-a-time), one requirement at a time.
3. [Review the risks](/docs/getting-started/quickstart#_8-review-the-risks).
4. Accept the [design](/docs/getting-started/quickstart#_9-accept-the-design) and the [tasks](/docs/getting-started/quickstart#_10-accept-the-tasks).
5. [Implement](/docs/getting-started/quickstart#_11-implement) and [archive](/docs/getting-started/quickstart#_12-archive) it.

## 8. Start the next slice

You do not have to wait for the first slice to be built. Once its proposal and specs are accepted, press :key-cap{k="s"} on the overview to start the next slice. The change panel reminds you with a line that starts `s  specify the next slice on the roadmap:`. (In the review, :key-cap{k="s"} means skip instead.)

The slices without a change are listed after the changes. Select one with :key-cap{k="↓"} (or a click) to read its summary and what it depends on. Press :key-cap{k="s"} (**▶ Start this slice**) to start it, or read why it cannot start yet.

A later slice's design, tasks and implementing wait until the slices before it are applied, because they build on that code. Applied means every task is ticked off, except those deferred until a deployment can verify them. An applied slice turns ✓ on its own. More in [Vision and roadmap](/docs/guides/roadmap).
