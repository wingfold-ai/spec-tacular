---
title: 'Quickstart: your first reviewed change'
description: From an existing OpenSpec project to a first change whose proposal, requirements, risks, design and tasks you reviewed and accepted, then implemented and archived.
---

In this quickstart you open spec-tacular on an existing OpenSpec project, set the ground rules, and take one change through the whole pipeline. You accept the proposal, review the specs one requirement at a time, then do the same for risks, design and tasks. Finally you implement the change and archive it.

You need spec-tacular, the OpenSpec CLI and Claude Code (or opencode) installed. See [Installation](/docs/getting-started/installation). Terms such as *schema*, *boundary* and *apply* are defined in the [Introduction](/docs#terms-used-in-these-docs).

## Which path you are on

What the start screen offers depends on your project. Check these in order, in your project folder, and stop at the first that matches:

1. **There is no `openspec/` folder, or `openspec init` was not run for your agent.** For Claude Code, `.claude/skills/openspec-apply-change/` is missing; for opencode, `.opencode/skills/openspec-apply-change/` is. The start screen says `OpenSpec is not initialized here…` or `OpenSpec is not set up for Claude Code here…`. Do [step 1](#_1-connect-openspec-to-your-agent), then press **Check again**.
2. **`spec-tacular/foundation/` exists, but not every question is answered.** The ground rules are under way. The start screen says `Ground rules: X of Y answered.` Press **Continue ground rules** and continue at [step 4](#_4-settle-the-ground-rules).
3. **There is no `spec-tacular/foundation/` yet, but `openspec/changes/` already holds a change** (a folder other than `archive/`). The start screen shows the number of changes and the buttons **Open project**, **New change** and **Ground rules**. Choose **Ground rules**. It sets the project up first, then asks the questions. Continue at [step 4](#_4-settle-the-ground-rules).
4. **No changes yet, and `openspec/specs/` contains a `.md` file or `openspec/changes/archive/` has an entry.** The start screen says `OpenSpec is here; spec-tacular is not set up yet.` Press **▶ Start** and follow this page.
5. **No changes yet, no `.md` file under `openspec/specs/`, and nothing in `openspec/changes/archive/`.** The start screen says the same as in 4, but spec-tacular treats the project as new: after **▶ Start** it asks for your vision. Follow [Start a new project](/docs/getting-started/new-project), or press **Not a new project — just start a change** (:key-cap{k="ctrl+n"}) and continue here at [step 4](#_4-settle-the-ground-rules).

## How the screens work

You meet these screens in this order:

- **Start screen.** The logo, one line on where the project stands, and buttons for the next step. :key-cap{k="h"} on the overview brings it back.
- **Ground rules.** One question at a time.
- **Overview.** The main screen. On the left is the **Changes** list. On the right is the **change panel** for the selected change: its pipeline bar, any warnings, and under **Next** the next step as a row of buttons.
- **Document view.** A proposal, risks, design or tasks, opened for reading, with buttons at the bottom.
- **Review.** One requirement or risk at a time.
- **Job pane.** :key-cap{k="ctrl+j"} from the overview or the review: the agents running in the background, and what each one read, ran and wrote.

On every screen, the bottom line lists the keys that work right now, and :key-cap{k="?"} lists every key. In a row of buttons the first is highlighted: :key-cap{k="enter"} presses it, :key-cap{k="←"} :key-cap{k="→"} choose another, and each button shows its own key. You can also click.

The core keys mean the same on every screen: :key-cap{k="a"} accepts, :key-cap{k="r"} revises with AI (:key-cap{k="ctrl+r"} on screens where you type), :key-cap{k="ctrl+e"} opens `$EDITOR`, :key-cap{k="y"} copies, :key-cap{k="q"} goes back (on the overview it quits). Some other letters depend on the screen:

| Key | On the overview | In the review |
| --- | --- | --- |
| :key-cap{k="n"} | start a new change | next requirement |
| :key-cap{k="s"} | start the next roadmap slice (a *slice* is one step of a new project's roadmap) | skip this requirement for now |
| :key-cap{k="f"} | open the ground rules | show all specificity flags |

In a document view with nothing to accept, the :key-cap{k="a"} button reads **✓ Looks good** and closes the document.

## 1. Connect OpenSpec to your agent

spec-tacular will not start work in a folder until `openspec init` has run there for your agent. In your project folder, run:

```bash
openspec init
```

When it asks which tools to set up, choose **Claude Code** (or **opencode**). If the project was set up for other tools only, run it again and add yours.

## 2. Open spec-tacular

In the same folder, run:

::code-group
```bash [Claude Code]
spec-tacular
```
```bash [opencode]
spec-tacular --driver opencode
```
::

To open a project in another folder, add `--cwd /path/to/project`.

spec-tacular opens on its start screen:

::terminal-block
---
title: start screen (trimmed)
lines: |
  spec-tacular
  spec-driven development — every requirement reviewed before it is built

  OpenSpec is here; spec-tacular is not set up yet.

  ▶ Start    Quit

  ~/my-app
  ←/→ choose · enter select · q quit · or click
---
::

**You should now see** a status line from the table [above](#which-path-you-are-on).

::tip
On a terminal at least 130 columns wide, a sidebar shows which agent and model is answering, what it has cost so far, and what it is doing right now. :key-cap{k="ctrl+b"} expands it.
::

## 3. Set up the project

Press :key-cap{k="enter"} on **▶ Start**. A spinner says `Setting up the project…`.

Setup installs the spec-tacular schema into `openspec/schemas/spec-tacular/` and points the project's `openspec/config.yaml` at it, so OpenSpec now orders the stages proposal → specs → risks → design → tasks. It also writes the ground rules files to `spec-tacular/foundation/`.

**You should now see** the ground rules screen, with a stepper at the top: `✓ Set up  ──  2. Ground rules  ──  3. First change`. If setup fails, the start screen shows `Setup failed:` and the reason.

## 4. Settle the ground rules

The ground rules are what every agent reads before it writes a proposal, spec or design for this project, so it builds on your decisions instead of inventing its own. They cover four areas: Domain, Stack, Architecture and Conventions.

On a project that already has specs in `openspec/specs/` or an archived change, you are asked all nineteen questions, domain first. The intro screen says so on its button: **▶ Begin — 19 questions**. A project with neither, such as a [new project](/docs/getting-started/new-project#_6-confirm-the-ground-rules), is asked fewer: the questions nobody can answer before code exists are left for later. Press :key-cap{k="enter"}.

::steps
### Answer the domain question

The first question is *What the system is for, and who uses it.* Type two sentences and press :key-cap{k="enter"}. Answers are saved as you go.

### Confirm or pick the rest

For the questions after that, an AI advisor proposes options for your project. While it works, the bottom line says `AI is thinking about “…”`. Two markers help you choose. ★ marks the option the advisor recommends. ⇐ marks an answer derived from your earlier answers; it is already selected. The box under the list shows in full what picking it writes.

Choose with :key-cap{k="↑"} :key-cap{k="↓"} and press :key-cap{k="enter"} to pick. To write your own answer, start typing. To adjust an option with AI first, press :key-cap{k="ctrl+r"}.

### Skip what you have not decided

Every question lists **↷ Skip — leave it for later** first. :key-cap{k="tab"} does the same. A skipped question does not block your first change.

### Finish

When every question is answered or skipped, a summary says how many are answered and how many are left for later. Press :key-cap{k="enter"} on **▶ Continue**.
::

::tip
**The fastest path:** press :key-cap{k="enter"} on each ⇐ (derived, already selected) or ★ (recommended) option, and press :key-cap{k="ctrl+f"} (*done — rest later*) as soon as you have answered what matters. The open questions are left for later and block nothing. Not sure what a question means? Press :key-cap{k="?"} or type `help` for a plain explanation, examples and simpler questions.
::

You can change any answer later with :key-cap{k="f"} on the overview, or by editing the files. More in [Ground rules (Foundation)](/docs/guides/foundation).

**You should now see** the overview. On a project without changes, the right-hand panel starts with `Ground rules are set. Next: your first change.`

## 5. Describe your first change

A change is one slice of work, small enough to review in one sitting. Think "add user login", not "build the app".

1. Press :key-cap{k="n"}, or click **+ New change**.
2. The panel **New change · 1 of 2 · what** asks *What do you want to change, and why?* Describe it in a sentence or two. The agent that drafts the proposal starts from this text. Press :key-cap{k="enter"}.
3. In **2 of 2 · name**, a name is proposed from your description: one appears at once, and a better one follows from the AI. Adjust it if you like. It must be lowercase words joined by dashes, such as `add-user-login`. :key-cap{k="tab"} shows the next suggestion. Press :key-cap{k="enter"} to create the change.

**You should now see** the change in the **Changes** list, and its change panel on the right:

::terminal-block
---
title: overview, change panel (trimmed)
lines: |
  add-user-login

  ◉ proposal ── ○ specs ── ○ risks ── ○ design ── ○ tasks ── ○ apply

  Next
  Write the proposal: why this change, and what it changes. Let an agent draft it, or write it yourself.

  ✦ Let an agent draft it  w    ✎ Write it myself  ctrl+e

  ←→ action  enter go  n new change  b report a defect  f ground rules  ctrl+j jobs  ? help  q quit
---
::

| Mark | Means |
| --- | --- |
| ✓ | accepted by you |
| ● | written, not yet accepted |
| ◉ | ready to write |
| ○ | blocked |

The last stage, `apply`, is implementing the tasks.

## 6. Draft and accept the proposal

Press :key-cap{k="w"} (**✦ Let an agent draft it**). To write it yourself instead, press :key-cap{k="ctrl+e"} (**✎ Write it myself**).

### While the agent drafts

The agent works in the background, and you can keep working. The change panel shows its progress live:

::terminal-block
---
title: change panel while drafting (trimmed)
lines: |
  Claude Code is drafting the proposal · …
  │ (the agent's latest output, line by line)

  It opens here for you to read when it is done. Keep working meanwhile.

  Watch the full log  ctrl+j
---
::

:key-cap{k="ctrl+j"} opens the job pane: what each agent read, ran and wrote, and every tool call it was refused. If a draft fails, the notice says `<change>/<artifact> failed — ctrl+j shows its log`. Read the log in the job pane. If it shows that the agent could not run, for example because it is not signed in, run `claude` (or `opencode`) once in a terminal and sign in, then draft again with :key-cap{k="w"}.

### Read and accept it

When the draft lands, it opens for reading, titled `add-user-login › proposal`. Scroll with :key-cap{k="↓"} :key-cap{k="↑"} or :key-cap{k="space"}. Look in particular at its `## Boundary`: the paths this change expects to touch. Then choose:

- :key-cap{k="a"} **✓ Accept it**
- :key-cap{k="r"} **↻ Redraft with feedback**: type what should change, and the agent redrafts it with that.
- :key-cap{k="ctrl+e"} **✎ Edit it** in your editor.
- :key-cap{k="q"} **← Back** to read it later. :key-cap{k="v"} on the overview opens it again.

Accepting starts nothing by itself. **You should now see** the notice `✓ The proposal of add-user-login is accepted — w drafts the specs`, and `✓ proposal` in the pipeline bar.

## 7. Review the specs, one requirement at a time

Press :key-cap{k="w"} to draft the specs. When they are written, the change panel says *Review the specs: N requirements waiting, one at a time.* Press :key-cap{k="enter"} on **▶ Review**.

The review shows one requirement with its scenarios. The first line names the capability and your position in the queue. The progress bar and counts stay at the bottom. The requirement in this example is made up; yours is whatever the agent wrote:

::terminal-block
---
title: review (example requirement, trimmed)
lines: |
  spec-tacular  ~/my-app › add-user-login › specs
  auth   requirement 1 of 4   [ADDED]

  Requirement: Sign in with email
  The system SHALL let a registered user sign in with their email and password.

    Scenario: Correct password
      - **WHEN** a user submits their email and correct password
      - **THEN** they are signed in

  ░░░░░░░░░░░░░░░░░░░░░░░░░░░░  0 accepted · 4 pending
  a accept · r revise with AI · x reject · d defer · ctrl+e editor · s skip · n/p move · pgdn scroll · ? help · q back
---
::

Decide each one:

| Key | Does |
| --- | --- |
| :key-cap{k="a"} | Accept it. The next open requirement comes up. |
| :key-cap{k="x"} | Reject it. You are asked `Why reject?`. |
| :key-cap{k="d"} | Defer it. You are asked `What would verify it?`, and a reason is required. |
| :key-cap{k="r"} | Revise it with AI. |
| :key-cap{k="s"} | Skip it for now. |
| :key-cap{k="n"} / :key-cap{k="p"} | Move to the next or previous requirement. |
| :key-cap{k="q"} | Back to the overview. Decisions are saved immediately. |

### Revise a requirement with AI

Press :key-cap{k="r"} and say what should change, for example "make the timeout configurable" or "split it into two scenarios". Press :key-cap{k="enter"} to send. A spinner says `The agent is revising it`. The agent answers with the revised requirement, shown as a diff against the file. Then:

- :key-cap{k="a"} writes it into the spec, replacing only that requirement.
- :key-cap{k="r"} asks for more changes. The agent sees every earlier request.
- :key-cap{k="q"} discards it.

Nothing is written before :key-cap{k="a"}. The revised requirement is pending again, so accept its new text with :key-cap{k="a"}. When you revise a rejected requirement, the prompt starts from your reason for rejecting it.

The review may also flag a requirement that names an endpoint, table or class too early. That flag is advisory and never blocks a stage. Details are in [Reviewing](/docs/guides/reviewing).

**You should now see** `✓ specs` in the pipeline bar once every requirement is accepted or deferred. If some are rejected, the change panel asks you to revise them first.

## 8. Review the risks

Press :key-cap{k="w"} to draft the risks. The agent lists what this change could break in `risks.md`: each risk with its hazard, the requirements it threatens, a severity, the guard that rules it out, and how a test checks it.

The draft opens for reading. Press :key-cap{k="a"} (**✓ Looks good**) to return, then :key-cap{k="enter"} on **▶ Review**. Risks are reviewed in the same queue as the requirements, one at a time, with :key-cap{k="a"} / :key-cap{k="x"} / :key-cap{k="d"}. More in [Risks](/docs/guides/risks).

**You should now see** `✓ risks` in the pipeline bar.

## 9. Accept the design

Press :key-cap{k="w"} to draft the design. It must answer every accepted risk by name, and the change panel names any risk it does not answer. Like the proposal, the design is read and accepted as a whole: :key-cap{k="a"} accepts it, :key-cap{k="r"} redrafts it with feedback.

### If the agent stops

If accepted requirements contradict each other or leave a decision open, the agent stops instead of designing around them. It writes a report instead of the design, and the report opens, titled *The agent stopped before writing the design*. It lists each conflict or gap, with the full text of every requirement involved. Its buttons:

- :key-cap{k="s"} **▶ Revise them in the review** opens the review on the first requirement involved.
- :key-cap{k="b"} **↩ Fix the …** redrafts what the design was drafted against, with your answer.
- :key-cap{k="w"} **↻ Draft the design again** drafts again, with your answer to what it raised, or as it is.
- :key-cap{k="ctrl+e"} **✎ Write it myself**.

Until the next draft, the change panel keeps a warning that starts with `⚠ The agent stopped instead of writing the design`, and :key-cap{k="o"} reopens the report. More in [The change pipeline](/docs/guides/pipeline).

**You should now see** `✓ design` in the pipeline bar.

## 10. Accept the tasks

Press :key-cap{k="w"} to draft the tasks: the checklist the agent will work through. It includes a guard task for each risk. Read it and press :key-cap{k="a"}.

**You should now see** the notice `✓ The tasks of add-user-login is accepted — w starts implementing`, and `✓ tasks` in the pipeline bar.

## 11. Implement

The change panel now says *Planning is done. Implement it — the agent opens right here, as if you had started it yourself.* Press :key-cap{k="w"} (**▶ Implement it in Claude Code**).

spec-tacular opens your agent in a new tab or window of your terminal: a new window under tmux, a new tab in kitty, WezTerm, GNOME Terminal, Konsole or iTerm. In a terminal that cannot open tabs, such as an IDE's, it opens a new window of your desktop's terminal instead. The session starts with the change's apply instructions as its prompt, so the agent begins working through the accepted tasks without you typing anything.

It runs in your own permission mode (auto, accept edits, or ask). The project's test commands, typechecker and linter, spec-tacular's own checks and OpenSpec's read-only commands never ask, so the questions it does ask are worth reading.

spec-tacular stays open and follows the tasks as they are ticked off. **You should now see** `◉ Being implemented in another tab — X of Y tasks ticked off so far` in the change panel.

::note
If no tab or window can be opened, the agent takes over spec-tacular's own terminal until it exits. Back in spec-tacular, the notice says how many tasks are ticked off, and :key-cap{k="w"} continues.
::

Once implementing has started, files changed outside the proposal's boundary are listed in the change panel. This is advisory: only you can tell whether reaching further was right.

**You know it is done** when the change panel says *Implemented: all N tasks are ticked off.*

## 12. Archive

The change panel now offers **▶ Archive it** (:key-cap{k="A"}). It shows what archiving would do, or why the change may not be archived yet. Press :key-cap{k="enter"} to archive, or :key-cap{k="esc"} for not now.

If archiving is refused, the box is titled **not yet** and says why. The usual reasons:

- **Requirements neither accepted nor deferred.** `Refused: N requirement(s) are neither accepted nor deferred.` Review them, or defer the ones that cannot be verified yet.
- **An implementation diff nobody accepted**, for a change in a consequence class that requires it (P0). In that case the change panel first asks you to read the code the agent wrote: press :key-cap{k="enter"} on **▶ Read the implementation**, then :key-cap{k="a"} to accept it. See [Consequence classes](/docs/advanced/consequence-classes).
- **Missing evidence**, when the project runs tests for evidence through `spec-tacular/verification.yaml`. `Refused: N item(s) of <change> have no current evidence.` Every accepted requirement and risk needs a passing test or an exception. See [Verification](/docs/advanced/verification).

More in [Implement and archive](/docs/guides/implement-and-archive).

Once archived, the accepted requirements merge into the baseline: the accepted specs in `openspec/specs/` that later changes build on. A deferred requirement waits in `spec-tacular/pending-validation.md` with what would verify it. **You should now see** the notice `Archived add-user-login: its requirements are now the baseline.` More in [Implement and archive](/docs/guides/implement-and-archive).

## What to commit

Commit `spec-tacular/` (the ground rules and other project records) and each change's `openspec/changes/<id>/review.md`, which lists what you accepted, rejected and deferred. Setup wrote `.spec-tacular/.gitignore`, which keeps this machine's state out of git. See [Files](/docs/reference/files).
