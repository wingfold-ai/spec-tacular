---
title: Consequence classes
description: Sort your code by what a failure would cost, P0 to P3, so risky changes get more rigor; diff review, guarded risks and waivers with reasons.
---

Not every change deserves the same rigor. A settings screen and an authorization check should not go through the same ceremony. Consequence classes let you say which code is which, so the extra checks land where a failure costs most.

## Why classes

You map areas of your code to a class, from P0 (highest consequence) to P3 (lowest). Each class turns rules on. A change is in the highest class it touches, and its class decides what it must show before it counts as done.

Without a `classes.yaml`, nothing changes: no change has a class, and no class rule applies. Every project starts that way.

## Write classes.yaml

Create `spec-tacular/classes.yaml` yourself. Nothing generates it.

```yaml
default: P2                      # code no area names
classes:
  P0:
    why: a wrong decision here lets unreviewed work through
    paths: [src/core/gate.ts, src/auth/]
  P1:
    why: a wrong total is visible to every user
    paths: [src/billing/**/*.ts]
tailoring:                       # a rule waived for a class, never without why
  - class: P0
    rule: diff-review
    reason: one developer; every merge is pair-reviewed
```

| Key | Meaning |
| --- | --- |
| `default` | The class of code no area names. Leave it out and such code adds no class |
| `classes.<P0–P3>.paths` | Files, folders or glob patterns in that class. Each class needs at least one |
| `classes.<P0–P3>.why` | What a failure in this code would cost. Shown to you and to the agents |
| `tailoring` | Rules waived for a class, each with a `reason` |

When a file falls in more than one area, the highest class wins.

## How a change gets its class

spec-tacular looks at a change twice.

1. **By its boundary.** The proposal names a `## Boundary`: the paths the change expects to touch. The change's declared class is the highest class those paths reach into. A change without a boundary is declared at the `default` class.
2. **By the files it changed.** Once implementing has started, the files changed on the branch count too. If any is in a higher class than the boundary declared, the change moves up, and the overview names the files that raised it:

```
! declared P2, but changed P0 code: src/auth/session.ts
```

Higher consequence always wins. A change cannot lower its class by declaring a narrow boundary and then reaching further.

## What each class requires

Each class turns rules on. Today there are two.

| Rule | Classes | What it requires |
| --- | --- | --- |
| `diff-review` | P0 | A person reads and accepts the implementation diff before the change counts as implemented |
| `guard-high-risks` | P0, P1 | A high-severity risk cannot be left unmitigated |

The class also decides how formal requirements are verified. Matrices, their harness and the harness check run only for P0 and P1 changes. See [Formal requirements](/docs/advanced/formal-requirements).

### diff-review: the agent cannot certify its own code

The agent wrote the code, so it cannot be the one to certify it. For a P0 change, ticking the last task off is not the end of implementing. The overview's next step becomes reading the code:

```
All tasks are ticked off. This is a P0 change: read the code the agent wrote, then accept it.
```

Read the diff with :key-cap{k="v"} on the overview and accept it with :key-cap{k="a"}, or from a shell:

```bash
spec-tacular diff add-export            # read it
spec-tacular diff add-export --accept   # accept what you just read
```

`--accept` records the diff as it is now, so run it only after reading that same output. Like every acceptance, it holds for that text: a later change to the code sends it back. Archiving is refused until it is accepted:

```
Refused: add-export is a P0 change and nobody has accepted its implementation diff.
Read it with `spec-tacular diff add-export`, then accept it with `--accept`.
```

On a roadmap, a P0 slice is not applied until its diff is accepted, so the slices after it wait too.

### guard-high-risks: no unmitigated high-severity risk

A risk can be left knowingly unmitigated with an `Unmitigated:` line that says why. In a P0 or P1 change, a high-severity risk cannot. The design is refused until the risk has a guard:

```
a P0 change cannot leave a high-severity risk unmitigated: "Export leaks other users"
```

Severities that start with `high`, `critical` or `catastrophic` count as high.

## Waive a rule, with a reason

Sometimes a rule does not fit your project. A single developer cannot have someone else read every P0 diff, but may have every merge pair-reviewed. Waive the rule for that class under `tailoring`, and say why.

A waiver without a reason is not applied. `spec-tacular classes` reports it:

```
Warning: tailoring: diff-review for P0 gives no reason, so it is not applied
```

A waived rule is named wherever it would have applied, with its reason. The overview of a P0 change shows:

```
! waived for P0: diff-review — one developer; every merge is pair-reviewed
```

A waived `guard-high-risks` lets the design through, with a warning naming the reason.

## See the map

```bash
spec-tacular classes
```

It prints the map, the rules each class turns on, and every change's class. Agents read the same map as part of their context.

::terminal-block
---
title: spec-tacular classes
lines: |
  $ spec-tacular classes
  # Consequence classes

  How much a failure would cost, by area of code. A change is in the
  highest class it touches; its class decides what it must show.

  - P0: `src/core/gate.ts`, `src/auth/` — a wrong decision here lets unreviewed work through
  - P1: `src/billing/**/*.ts` — a wrong total is visible to every user
  - everything else: P2

  - P0: a high-severity risk cannot be left unmitigated
  - P0: (waived: one developer; every merge is pair-reviewed) a person reads and accepts the implementation diff before the change counts as implemented
  - P1: a high-severity risk cannot be left unmitigated

  add-export  P0 (declared P2)
---
::

`spec-tacular classes` exits 1 when `classes.yaml` has problems, such as an unknown class or a class with no paths. Without a `classes.yaml`, it prints an example and exits 0.
