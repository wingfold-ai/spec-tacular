Prose can be read two ways. Where a requirement turns on a decision or on timing, you can give it a formal form as well. Writing the formula makes the open questions visible, and the formula gives you tests you do not have to choose.

::warning
Formal forms are optional, and their heaviest part is expensive. In evaluation runs of two small apps, the matrices and the harness cost most of a change's extra time and caught little the ordinary tests did not. By default, matrices and the harness check run only for changes in class P0 or P1. Use formal forms where a failure costs most.
::

## Add a formal form

A formal form follows the requirement's text, in a fenced block named `formal`. It is part of what you accept.

````markdown
### Requirement: Archive only finished changes
The system SHALL allow archiving only when every task is applied, every spec
is accepted and no stop is open.

#### Scenario: A task is still open
- **WHEN** a task is neither ticked nor deferred
- **THEN** archiving is refused

```formal
decision: archive_allowed = tasks_applied AND specs_accepted AND NOT stop_open
fret: upon request_sent Client shall within 3 ticks satisfy response | timeout_error
asked: Does a deferred task count as open? — No; deferred tasks are excused.
```
````

| Line | What it says |
| --- | --- |
| `decision:` | An output defined by a boolean condition: `AND`, `OR`, `NOT`, `XOR`, `->`, `<->` and comparisons |
| `fret:` | NASA FRET's structured English, FRETish: scope, condition, component, timing, response |
| `asked:` | A question writing the formula forced, and the agent's proposed answer |

A form whose formula cannot be read, names a variable the glossary does not have, or defines an output differently from another requirement holds up the design. The overview names the combination where the two differ.

## The glossary

The variables come from `spec-tacular/glossary.yaml`. Each has a role, a type, a meaning, and where its value comes from.

```yaml
variables:
  timer_running: { role: input, type: bool, meaning: a timer is running, source: the data file }
  same_project:  { role: input, type: bool, meaning: started on the running timer's project }
  file_version:  { role: input, type: int, range: [1, 3], meaning: the data file's schema version }
constraints:
  - same_project -> timer_running      # same project as the running one needs a running one
```

| Field | Values |
| --- | --- |
| `role` | `mode`, `input`, `output`, `internal` |
| `type` | `bool`, `int`, `float`, `enum` with `values:`. `boolean`, `integer` and `number` are read as the first three |
| `meaning` | What the variable stands for, in words |
| `source` | Where its value comes from in the system |

**Constraints** say which combinations cannot happen, so the matrix does not ask for tests of them.

```bash
spec-tacular glossary
```

This lists every variable, which requirements use it, and what is missing: variables used but not defined, and variables without a source. A variable without a source cannot be observed, and so cannot be monitored. Press :key-cap{k="g"} on a review card to open the glossary in `$EDITOR`.

## Read back in plain words

The review reads a formal form back as a sentence, with what each variable means:

> *archive_allowed is true exactly when tasks_applied and specs_accepted and not stop_open*

A wrong formula is easier to catch as a wrong sentence than as a formula.

A requirement without a formal form is flagged for the words it leaves undefined, such as *promptly*, *large* or *gracefully*.

## Answer the questions it asked

Writing a formula forces questions the prose let slide: an empty list, every member or refused? Each `asked:` line is a question in the review, right before its requirement. The agent's answer is only a proposal. Deciding it is yours.

- :key-cap{k="a"} accepts the proposed answer.
- :key-cap{k="r"} gives your own, and the requirement is revised with it.

The answers go into the prose, which stays what the specs promise, and each gets a scenario of its own.

## Revise with the glossary

Revising a requirement with AI (:key-cap{k="r"}) can change the glossary along with it. The agent returns the entries its formula needs, shown above the diff:

```
+ clock_behind (input, bool) — …
```

On accept they are written into `glossary.yaml`, comments and all. A variable the formula still leaves undefined is named.

## Generated test matrices

A formal form's tests are generated, not chosen.

```bash
spec-tacular matrix add-export
```

The matrix also shows in the review, under the formula. It is folded to one line per matrix until :key-cap{k="t"} opens it.

```
Matrix (3 conditions): alarm = armed & voltage > 9 & voltage < 20
  × D1   armed=F, voltage > 9=F, voltage < 20=F: cannot happen — no value of voltage makes …
    D2   armed=F, voltage=9 → alarm=F
  ◆ D6   armed=T, voltage=9 → alarm=F    [MC/DC: voltage > 9]
  ◆ D8   armed=T, voltage=10 → alarm=T   [MC/DC: armed, voltage > 9, voltage < 20]
    B4   armed=T, voltage=19 → alarm=T   (edge of voltage < 20)
```

**A decision** gets every combination of its conditions, each made concrete, with the output the formula requires. A comparison is set at its boundary.

- `×` marks rows nothing can produce, or that the glossary's constraints rule out. They are not run.
- `◆` marks the MC/DC rows, where one condition alone changes the outcome. A condition with no such row is reported as dead or coupled.
- `B` rows walk each comparison across its edge.

**A FRETish requirement** gets step sequences: the trigger firing once, never, held, again while the first is pending, late, or outside its scope. Each comes with checks over the response at a step, or at some, every or no step of a window. Responses that break the checks come with it, to test the checker.

### Which rows must pass

Each row becomes a test named `[req:…] [row:D7]`. The change's consequence class decides which rows must pass for the requirement to count as verified:

| Class | Rows required |
| --- | --- |
| P0 | Every row |
| P1 | The MC/DC and boundary rows of a decision, and every step sequence of a FRETish requirement |

A matrix whose formula or glossary changed is out of date, and the overview says so.

### Write the tests

```bash
spec-tacular matrix add-export --write
```

`--write` does three things:

1. Writes the matrices to `spec-tacular/matrix/`. They outlive the change.
2. Copies a dependency-free runner into the project.
3. Writes a table-driven test per matrix.

On the overview, :key-cap{k="M"} writes the matrices and their tests too, for when a revised formula leaves a matrix out of date.

The one part you write by hand is the **harness**: how to set each input in the real code and read each output from it.

## Connect the harness

A green matrix proves nothing if the harness answers for the code, or reads the wrong place. So a matrix's results count only once its harness is **connected**. Until then, its requirement's evidence is *not connected* rather than passing, and archiving waits.

### A mapping, not code, where it can be

`<component>.mapping.yaml`, in `test/support/harness/` by default, binds each variable to an export or a field of the production module. It is data, so it cannot compute an answer.

```yaml
module: src/archive/decide.ts
inputs:
  tasks_applied: { arg: tasksApplied }
outputs:
  archive_allowed: { call: archiveAllowed }
```

Harness code is the fallback. It exports `harness`, a function returning `{ reset?, drive(name, value), observe(name), tick? }`. It must import production code, and never the matrix.

With a `probe`, every input is read back after each drive. A drive that moved another input fails the row, which would otherwise pass for the wrong reason.

### Check it with coverage and mutants

```bash
spec-tacular harness add-export --check
```

The check runs in two passes.

1. **Coverage.** The matrix tests run with coverage, and must execute the code the harness names.
2. **Mutants.** Then they run against small changes to the code they ran: `&&` to `||`, a `!` dropped, `>` to `>=`. Some row must catch each one.

What is mutated is every source file the coverage report shows executed, not only what the harness imports, since the decision logic is usually a layer further in. Only executed lines are mutated. Test files and test doubles (`test-support/`, `fakes/`, `in-memory-…`) never are, nor anything `matrix.exclude` lists. The budget, `matrix.mutants` (default 32), is shared out over the files. Mutants run in a scratch copy; the real source is never written.

A harness that computes the answer itself passes every row and catches no mutant:

```
archive  NOT CONNECTED  (code: test/support/harness/archive.ts)
    - the matrix tests never execute src/archive/decide.ts
    - 3 of 3 changes to the code went unnoticed — the matrix does not reach
      that code, or the requirements allow what the change does …
```

Each matrix is judged by its own tests: every item's matrix tests must catch some mutant themselves. One weak harness does not make its neighbours *not connected*.

### A surviving mutant is a question

A surviving mutant is a question about the requirements as much as the harness. A client that always "responded" met *within 3 ticks satisfy response*. That is how a missing requirement shows up.

It is one finding for the component, settled once:

- Add the requirement that rules it out.
- Or, where the code is free to differ, allow it:

```bash
spec-tacular harness add-export --allow-survivors "the CLI flag parsing is not specified"
```

The reason is recorded with the survivors it allowed, in `.spec-tacular/harness/<component>.allowed.json`, which is committed. New survivors are asked about again. A matrix that caught none of its changes cannot be allowed: its harness does not reach the code.

### Review each binding

Once the harness is written, the overview's next step is reviewing it. Each binding is an item in the change's review queue, shown beside what its variable means:

> *tasks_applied · Means: every task ticked or deferred · Set by: arg tasksApplied — in src/archive/decide.ts*

Accept each one in the review, or from a shell after reading them:

```bash
spec-tacular harness add-export --accept
```

An edit to the harness sends a binding back.

## Where it applies

Matrices, their harness and its check are for the code whose failure costs most: changes in class P0 or P1.

Everywhere else, and in a project without consequence classes, a formal form still specifies. It is read back, checked for conflicts, and asks its questions. Its requirement is tested like any other, with a tagged test per scenario, and the tasks plan no harness.

To change this, set `matrix.verify` in `spec-tacular/verification.yaml`:

| Value | Matrices and harness check run for |
| --- | --- |
| `auto` (default) | Changes in class P0 or P1 |
| `always` | Every change with a formal form |
| `never` | No change |

## Check against NASA FRET

spec-tacular reads FRETish with its own semantics, and every matrix inherits that reading. So it can be checked against NASA FRET itself.

### fret check

```bash
spec-tacular fret check [<change>]
```

For each FRETish requirement, this takes FRET's own finite-trace formula (`fretcli formalize -l ft-fin`) and compares it with spec-tacular's verdict. It compares on the matrix's sequences and on thousands of seeded random traces, and names any trace they disagree on. It exits 1 on a disagreement.

Set `fret.cli` in `verification.yaml` to the command before `formalize`:

```yaml
fret:
  cli: npm run --silent --prefix ~/fret/fret-electron start-cli --
```

`SPECTACULAR_FRET_CLI` overrides it. FRET's answers are cached in `spec-tacular/fret/formulas.json`. Once that file is committed, the check also runs where FRET is not installed.

::warning
`fret.cli` is a shell command, and spec-tacular runs it as written, the way `npm run` runs a package's scripts. In a repository you did not write, read `fret.cli` before running `fret check` or `fret realizability`, or set `SPECTACULAR_FRET_CLI` to your own FRET command, which takes precedence.
::

### fret export

```bash
spec-tacular fret export [<change>] [--out <dir>]
```

This writes the FRETish requirements and the glossary, as FRET's Mode, Input, Output and Internal variables, to `spec-tacular/fret/export/` by default. Import them into FRET for its realizability checking, simulator and test generation. Decisions are not FRETish and stay out.

```bash
spec-tacular fret realizability <project> <component>
```

This runs FRET's own realizability check on requirements imported into FRET.

## Monitor a recorded run

```bash
spec-tacular monitor run.jsonl [<change>]
```

`monitor` checks a recorded run against every formal requirement whose variables it records, decisions and FRETish alike. This is the offline half of runtime verification. The run comes from an end-to-end test or from production, with one JSON object of variable values per step:

```
{"tasks_applied": false, "specs_accepted": true, "stop_open": false, "archive_allowed": false}
{"tasks_applied": true, "specs_accepted": true, "stop_open": false, "archive_allowed": true}
```

A requirement whose variables the run does not record is listed as not recorded. `monitor` exits 1 on a violation. `fret check` flags the requirements that cannot be monitored on a running system, such as an unbounded *eventually*.
