title: Verification evidence and CI
description: Tag tests with the requirements and risks they verify, build the evidence matrix, keep an append-only log, and gate archiving and CI on it.
---

A ticked task is a claim. A passing test is evidence. Once you tell spec-tacular how to run your tests, it links each accepted requirement and risk to the tests that verify it, and a change is not archived until every one of them is proven or excepted.

## Tag your tests

A test names what it verifies in its own name. This works in any language and any test framework, because spec-tacular reads only the names in a JUnit report.

| Tag | Verifies |
| --- | --- |
| `[req:<capability>#<slug>]` | A requirement |
| `[risk:<change>#<slug>]` | A risk's guard |

```ts
test('[req:export#export-data] exports the caller\'s data', () => { /* … */ })
test('[risk:add-export#export-leaks-other-users] never includes another user\'s rows', () => { /* … */ })
```

You do not have to work out the tag. For an item without a test, `spec-tacular evidence` prints the exact tag to use. One test may carry several tags.

## Tell spec-tacular how to run them

`spec-tacular init` writes `spec-tacular/verification.yaml` with the lines for common runners commented out. Evidence stays off until you uncomment one. The tasks of a first change fill it in.

```yaml
command: bun test --reporter=junit --reporter-outfile=.spec-tacular/junit.xml
report: .spec-tacular/junit.xml   # any JUnit XML: vitest, jest, pytest --junitxml, …
```

The starter has ready lines for Bun, Vitest, Jest with `jest-junit`, and pytest. `command` and `report` go together; the rest of the file's keys are listed in [Configuration](/docs/reference/configuration#verificationyaml).

::note
With `verification.yaml` in place, evidence is required: archiving waits for it. Without one, nothing is collected and nothing is required.
::

## Run the tests and read the matrix

```bash
spec-tacular evidence --run          # run the tests, record what they found
spec-tacular evidence add-export     # print the matrix for one change
```

`--run` runs `command`, reads `report`, and appends what it found to the evidence log. It then prints the verification matrix for every change, or only the one you name:

::terminal-block
---
title: spec-tacular evidence
lines: |
  $ spec-tacular evidence add-export
  add-export  1/2 verified
    passing  test          export#export-data  Export data
             [req:export#export-data] exports the caller's data
    missing  test          risks#export-leaks-other-users  Export leaks other users
             name a test with [risk:add-export#export-leaks-other-users]
---
::

Each line shows the item's state, how it is verified, its id and its name. The tests that count for it follow underneath.

`--run` also lists orphans: a test whose tag names a requirement or change that does not exist.

```
  orphan: [req:export#old-name] in "exports csv" names nothing that exists
```

## States

The states are kept apart, so a stale pass never reads as a pass.

| State | Meaning |
| --- | --- |
| `passing` | Its tests passed on their latest run, against the text you accepted |
| `failing` | A test for it failed on its latest run |
| `missing` | No test names it yet, or no run has recorded one |
| `stale` | The item's text, or the test's file, changed since it passed |
| `not connected` | Its matrix rows passed, but the harness is not shown to reach the code. See [Formal requirements](/docs/advanced/formal-requirements) |
| `excepted` | Waived with a reason, or deferred. The matrix prints it as `waived`, with the reason |

Each record carries a hash of the item's text and of the test's file, which is how an edit makes evidence stale.

## Not everything is a test

Some requirements are verified by other means. Say so in the requirement:

```markdown
**Verified by:** inspection
```

The methods are `analysis`, `inspection` and `demonstration`. A person records the check, bound to the item's text as it is now:

```bash
spec-tacular evidence -c add-export --sign export#audit-trail \
  --method inspection --note "read the log format against the audit policy"
```

Item ids are the ones `spec-tacular evidence <change>` shows. An edit to the item later makes the sign-off stale.

## Waive an item, with a reason

```bash
spec-tacular evidence -c add-export --waive export#export-data \
  --reason "covered by the vendor's certified export"
```

A waiver needs a reason, and it is reported as excepted, never as verified. Two kinds of item need no waiver:

- A deferred requirement is excepted by its deferral.
- A risk left `Unmitigated:` needs none.

## The evidence log

Evidence lives in `.spec-tacular/evidence/<change>.jsonl`: one line per test result, sign-off or waiver. Nothing in it is ever rewritten. A new run appends, and the latest records decide an item's state.

At archive time, each item's evidence is written into the change's `review.md`, which is committed.

## Archiving waits for evidence

With `verification.yaml` in place, archiving is refused while any accepted requirement or risk is not passing or excepted:

```
Refused: 1 item(s) of add-export have no current evidence.
  - missing: risks#export-leaks-other-users

See `spec-tacular evidence add-export`; `--run` runs the tests.
```

The overview says the same once implementing has started:

```
! evidence 1/2: 1 without evidence — see `spec-tacular evidence add-export`
```

## Requirements verified after deployment

A requirement that needs a running environment can be deferred. The change archives without it: the verified requirements merge into `openspec/specs/`, and the deferred one waits in `spec-tacular/pending-validation.md` with what would verify it.

Once you have verified it, move it into the baseline:

```bash
spec-tacular pending
spec-tacular verify data-export --requirement "Export completes against a deployment"
```

`verify` writes the requirement into `openspec/specs/<capability>/spec.md` and runs `openspec validate` on it.

## Gate CI on it

`spec-tacular evidence` exits 1 while any item of any change is missing, failing, stale or not connected, so a CI step can fail on it. `spec-tacular hazards` exits 1 while a hazard is open: a guard failing, or no control verified by a test.

| Command | Exit code |
| --- | --- |
| `spec-tacular evidence` | 0 when every item is passing or excepted, or when there is no `verification.yaml`. 1 otherwise |
| `spec-tacular evidence --run` | As above, after the run. 1 if the tests wrote no report |
| `spec-tacular hazards` | 1 when a hazard is open |

A GitHub Actions job needs the OpenSpec CLI, spec-tacular, and your test runner:

```yaml
- run: npm i -g @fission-ai/openspec
- run: curl -fsSL https://spec-tacular.app/install.sh | sh
- run: echo "$HOME/.local/bin" >> "$GITHUB_PATH"
# … set up your test runner here …
- run: spec-tacular evidence --run
- run: spec-tacular hazards
```

::caution
The evidence log is in `.spec-tacular/`, which the `.gitignore` written by `init` keeps out of git. A fresh CI checkout starts with no earlier runs, sign-offs or waivers. `--run` records the test results again, but an item verified by a sign-off or excepted by a waiver on your machine shows as `missing` there.
::

The `curl` line works only once the repository is public. While it is private, the install script can download only through a signed-in GitHub CLI (`gh`), which a CI job would have to set up with a token that can read the repository; see [Installation](/docs/getting-started/installation).

## Write tests that can fail

The review flags a requirement whose scenarios are all the happy path:

```
! no scenario says what must not happen, or how it fails — a negative test needs one
```

A negative test needs a scenario that says what must not happen. Add one before you accept the requirement.
