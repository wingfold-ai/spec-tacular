---
title: Files and git
description: What spec-tacular writes into a project, where, and which of it belongs in git.
---

spec-tacular writes into three places: OpenSpec's own folder, `spec-tacular/` for what people read and commit, and `.spec-tacular/` for this machine's state. In `openspec/` it writes only the schemas, the `schema:` line of `config.yaml` and each change's `review.md`. Archiving also takes deferred requirements out of the change's spec files before `openspec archive` runs, and `spec-tacular verify` moves a requirement into `openspec/specs/`.

## openspec/

| Path | What it holds |
| --- | --- |
| `openspec/schemas/spec-tacular/` | The schema that sequences `proposal → specs → risks → design → tasks`. Installed by `init`; `--force` replaces it |
| `openspec/schemas/spec-tacular-defect/` | The schema a defect change uses. Installed by `init` next to the main one |
| `openspec/config.yaml` | `init` rewrites only its top-level `schema:` line. Changes already in flight keep their schema |
| `openspec/changes/<id>/review.md` | The review record of one change: what was accepted, with the questions' answers; rejected, with why; deferred, with what it waits for; allowed or waived |
| `openspec/specs/<capability>/spec.md` | The baseline. Archiving merges accepted requirements here; `verify` moves a pending one here |

`review.md` is rewritten from the review state on every decision and once more before archiving, so `openspec archive` moves it with the change. It reads the same without spec-tacular. Hand edits to it are overwritten.

## spec-tacular/

Everything here is meant to be committed: it is what people read, and what every agent reads as context.

| Path | What it holds |
| --- | --- |
| `foundation/` | The ground rules: `domain.md`, `stack.md`, `architecture.md`, `conventions.md`. Unanswered questions say `TBD`; questions left for later say *Decide later* |
| `decisions/` | ADRs, `NNNN-<slug>.md`, promoted from a design with :key-cap{k="p"} |
| `hazards/` | The hazard register, `NNNN-<slug>.md`. Accepted risks join it when their change is archived |
| `vision.md` | The vision and the interview |
| `roadmap.yaml` | The vision and an ordered list of slices |
| `glossary.yaml` | The variables formal requirements are written over, and their constraints |
| `pending-validation.md` | Deferred requirements waiting on validation, with what would verify each |
| `classes.yaml` | Consequence classes. You write this file; nothing creates it |
| `verification.yaml` | How to run the tests for evidence. `init` writes a starter, all comments |
| `lint.json` | `{ "allow": [...] }`: values the specificity check never flags. You write this file |
| `matrix/` | Test matrices, one JSON file per matrix, written by `matrix --write` |
| `fret/formulas.json` | FRET's answers, cached by `fret check`. Committed, the check also runs where FRET is not installed |
| `fret/export/` | Default output of `fret export` |

## .spec-tacular/

This folder is mostly this machine's state. `init` writes `.spec-tacular/.gitignore`, which ignores everything here except the records of what a person decided:

```yaml
# generated-by: spec-tacular <version>
# This machine's state, kept out of git. Kept in: what a person decided.
*
!.gitignore
!review/
!review/*.json
!harness/
!harness/*.allowed.json
```

`init` does not overwrite a `.gitignore` that is already there.

| Path | In git | What it holds |
| --- | --- | --- |
| `review/<change>.json` | yes | The review decisions and document acceptances of a change |
| `harness/<component>.allowed.json` | yes | Surviving mutants you allowed, with the reason |
| `harness/<component>.json` | no | The last harness check |
| `evidence/<change>.jsonl` | no | The evidence log: test results, sign-offs and waivers, appended and never rewritten |
| `jobs/` | no | Background jobs and their logs |
| `stops/<change>/<artifact>.md` | no | The report of a draft that stopped |
| `implementing/` | no | The scripts and markers of implementing sessions, and `sessions.jsonl` |
| `usage.jsonl` | no | What the AI cost, so a restart keeps the total |
| `vision-session.json` | no | The vision interview in progress |
| `foundation-advice.json` | no | What the advisor proposed for the ground rules |
| `junit.xml`, `coverage/` | no | Test reports, at the paths the verification starter uses |

::warning
If git ignores any of the records spec-tacular keeps for the repository, `init` says so. Ignored, the review decisions are lost with the machine. Keep `spec-tacular/`, `openspec/changes/` and `.spec-tacular/review/` in git.
::

## Files written into your code

`matrix --write` also writes into the project, at paths you can change under `matrix:` in `verification.yaml`:

| Default path | What it is |
| --- | --- |
| `test/support/spec-tacular-matrix.ts` | A dependency-free runner for the matrix tests |
| `test/matrix/` | One table-driven test file per matrix |
| `test/support/harness/` | Where the harnesses go, one per component: `<component>.mapping.yaml` or `<component>.ts`. You write these |

The runner and the generated tests never count as files changed outside a change's boundary.

## The generated-by marker

The Markdown and YAML documents spec-tacular writes itself start with a marker line: `<!-- generated-by: spec-tacular <version> -->` in Markdown, `# generated-by: spec-tacular <version>` in YAML.

- The version is the one that created the file. It is never rewritten, so an upgrade does not touch every file in the repository.
- The marker is not content: adding it never reopens a signed-off document.
- The proposal, specs, design and tasks the agents draft are left as they wrote them, without a marker.

These are the Foundation, ADRs, hazards, `vision.md`, `roadmap.yaml`, a `glossary.yaml` it creates, `review.md` and `.spec-tacular/.gitignore`; the `verification.yaml` starter and `pending-validation.md` carry none. A code search for `generated-by: spec-tacular` finds the ones that do.
