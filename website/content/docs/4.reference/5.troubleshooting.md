title: Troubleshooting
description: The problems spec-tacular reports, what each message means, and how to get past it.
---

Each section starts with what spec-tacular says, quoted as it appears.

## OpenSpec is not initialized

```
OpenSpec is not initialized here. Run `openspec init` in this folder first, and choose Claude Code.
```

spec-tacular builds on OpenSpec and will not set a project up without it. `openspec init` asks which agents to set up, so it is yours to run:

```bash
openspec init
```

Then press *Check again* on the start screen, or run `spec-tacular init`.

From the command line, a folder without `openspec/` gives `No openspec/ directory in <dir>.` Only the TUI opens there, to guide you through setting it up.

## OpenSpec is set up for another agent

```
OpenSpec is not set up for Claude Code here. Run `openspec init` in this folder again, and choose Claude Code.
```

`openspec init` installs the workflow's skills for each agent you pick. spec-tacular checks for them for the driver you run, `claude` by default. Run `openspec init` again and choose that agent, or start spec-tacular with the agent you did set up:

```bash
spec-tacular --driver opencode
```

## The openspec command is missing

```
The `openspec` command was not found.
Install it with `npm install -g @fission-ai/openspec`.
```

spec-tacular drives the OpenSpec CLI, which is installed separately:

```bash
npm i -g @fission-ai/openspec
```

If `openspec` is installed somewhere off your `PATH`, point at it with `--openspec-bin <path>`. A message that `openspec … did not return JSON` with `No output. Is the openspec CLI installed and on PATH?` points at the same problem.

`` The folder `<dir>` does not exist. `` means `--cwd` names a folder that is not there.

## The agent is not installed

When the agent's command is not on your `PATH`, the AI parts of the TUI say `` `claude` is not installed `` and the setup works without suggestions. Install Claude Code or opencode, or pick the one you have with `--driver`.

`Unknown agent driver '<name>'. Known drivers: claude, opencode.` means `--driver` has a typo.

When the agent is installed but its requests fail, the ground rules show `AI suggestions failed:` followed by the agent's message. These requests are not retried automatically. Run the agent on its own to see what it needs.

## Installing from a private repository

```
error: could not find the latest release of mhoegger/spec-tacular (a private repository needs gh, signed in)
```

While the repository is private, the install script can only download through the GitHub CLI. Sign `gh` in with access to the repository, then fetch the script through it:

```bash
gh api repos/mhoegger/spec-tacular/contents/install.sh -H 'Accept: application/vnd.github.raw' | sh
```

If the script says `note: <dir> is not on your PATH`, add that folder to your `PATH`, or install elsewhere with `SPECTACULAR_INSTALL_DIR`.

## Implementing does not open a new tab

*Implement it* opens your agent in a new tab of tmux, kitty, WezTerm, GNOME Terminal, Konsole or iTerm. In a terminal that cannot open tabs, such as an IDE's, it opens a new window of the desktop's terminal instead: on macOS, Terminal; on Linux, GNOME Terminal, Konsole or `x-terminal-emulator`, whichever is installed.

When no tab or window can be opened, the agent takes over spec-tacular's own terminal until it exits. spec-tacular then reads the ticked tasks and says `Back from Claude Code: 3 of 5 tasks ticked off — w continues`. This is a fallback, not an error.

## Copy and paste do not work

Copying uses `wl-copy`, `xclip`, `xsel` or `pbcopy`. Without them, or over SSH, copying goes through the terminal with OSC 52.

- `No clipboard tool found (wl-copy, xclip, xsel or pbcopy), and the terminal does not take OSC 52`: install one of the tools, or use a terminal that supports OSC 52. Most do, and so does tmux.
- `No clipboard tool found (wl-paste, xclip, xsel or pbpaste) — paste with ctrl+shift+v instead`: use the terminal's own paste.

Over SSH, :key-cap{k="ctrl+v"} cannot read your local clipboard. :key-cap{k="ctrl+shift+v"} or a middle click pastes through the terminal and works everywhere.

## The usage sidebar is missing

The sidebar needs a terminal at least 130 columns wide, so it never squeezes the screen beside it. On a narrower terminal, :key-cap{k="ctrl+b"} still opens the usage details full width.

## The agent asks for permission

The implementing session runs in your own permission mode, so it asks about what that mode asks about. The project's tests, its typechecker and linter, spec-tacular's checks and read-only commands are already allowed. What it still asks about is worth reading.

Drafting agents run headless and cannot ask. A tool call they need that is not allowed is refused, and the jobs pane (:key-cap{k="ctrl+j"}) lists every refused call. To allow more, add flags with `SPECTACULAR_CLAUDE_ARGS`. See [Permissions](/docs/reference/configuration#permissions).

## The ground rules are not settled

```
Refused: the project's ground rules are not settled yet
```

A change's first artifact waits until every Foundation question is answered or left for later. The blockers list the open questions. Answer them with :key-cap{k="f"} in the TUI, or see them with:

```bash
spec-tacular foundation
```

In the ground rules, :key-cap{k="ctrl+f"} leaves the rest for later and moves on.

## The design is refused

```
Refused: design is not ready to be written
  - specs: 2 pending of 5 requirements
```

An artifact is refused until the ones it requires are accepted, not just written. The lines under it say what is missing. Review it first: open spec-tacular, select the change and press :key-cap{k="enter"}.

Other blockers you may see for the design:

- `a P0 change cannot leave a high-severity risk unmitigated: "<risk>"`: give the risk a guard, or waive `guard-high-risks` with a reason. See [Consequence classes](/docs/advanced/consequence-classes).
- `the formal form of "<requirement>": …`: fix the formula or add the missing variable to the glossary. See [Formal requirements](/docs/advanced/formal-requirements).
- `<change> is not applied yet`: the slice builds on the code of an earlier one, which is not implemented yet.

## Archiving is refused

| Message | What to do |
| --- | --- |
| `Refused: 2 requirement(s) are neither accepted nor deferred.` | Review them: accept or defer each one |
| `Refused: <change> is a P0 change and nobody has accepted its implementation diff.` | Read it with `spec-tacular diff <change>`, then accept it with `--accept` |
| `Refused: 3 item(s) of <change> have no current evidence.` | See `spec-tacular evidence <change>`; `--run` runs the tests |
| `Its harness is not reviewed yet` | Read the harness, then accept it in the review, or with `spec-tacular harness <change> --accept` |

Use `spec-tacular archive <change> --dry-run`, or :key-cap{k="A"} in the TUI, to see what archiving would do without writing anything.

## Something changed since you accepted it

An acceptance holds for the text you read. When a document or requirement changes afterwards, it waits to be read again:

- A requirement shows `! changed since you marked it accepted — review it again`, and the overview counts `requirement(s) changed since you accepted them`.
- A document's next step says `The design changed since you accepted it. Read it again, then accept it or ask for changes.`
- For a P0 change: `The code changed since you accepted it. Read the implementation diff again, then accept it.`

Read it and accept it again. Ticking tasks off while implementing does not count as a change.

## An agent stopped instead of writing

```
⚠ The agent stopped before writing the design of add-export
```

An agent stops rather than design around requirements that contradict each other or leave a decision open. Its report opens with each conflict and the requirements involved. Revise the requirements in the review (:key-cap{k="s"}), fix what it was drafted against (:key-cap{k="b"}), or draft it again with your answer (:key-cap{k="w"}). :key-cap{k="o"} on the overview reopens the report.
