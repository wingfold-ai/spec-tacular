Everything the TUI does is also a command. Run `spec-tacular` with no command for the TUI, or `spec-tacular --print` for the same overview as text.

```bash
spec-tacular --help
```

## Global options

These options work with every command.

| Flag | Meaning |
| --- | --- |
| `-p`, `--print` | Print the overview as text and exit |
| `-c`, `--change <name>` | The change to act on |
| `--cwd <dir>` | Project root. Default: the current directory |
| `--openspec-bin <path>` | Path to the `openspec` binary. Default: `openspec` on your `PATH` |
| `--driver <name>` | Agent to run: `claude` or `opencode`. Default: `claude` |
| `-f`, `--force` | Overwrite an existing schema install (`init`) |
| `-h`, `--help` | Show the help |
| `-V`, `--version` | Show the version |

Every command except the TUI needs an OpenSpec project. Without an `openspec/` folder in `--cwd`, it prints `No openspec/ directory in <dir>.` and exits 1. Where a command takes a `<change>` argument, `-c <change>` works as well.

## Exit codes

Every command exits 0 on success and 1 on failure or refusal; `fret realizability` passes on FRET's own exit code. The commands that check something also exit 1 when the check finds a problem, so CI can run them as gates:

| Command | Exits 1 when |
| --- | --- |
| `instructions`, `run` | The artifact is refused: its prerequisites are not accepted |
| `archive` | Archiving is refused |
| `evidence` | Any change has an item that is not passing or excepted |
| `hazards` | A hazard is open: one of its guards is failing, or none of its controls is verified by a test |
| `classes` | `classes.yaml` has problems |
| `glossary` | A formal form or the glossary has errors |
| `matrix` | A formal form has errors, so it has no matrix |
| `harness` | A harness is not connected |
| `fret check` | spec-tacular and FRET disagree on a trace |
| `monitor` | A recorded run violates a formal requirement |

## The overview and the TUI

```bash
spec-tacular                 # the TUI
spec-tacular --print         # the overview as text, also over a pipe and in CI
```

`--print` renders the same model as the TUI. It also prints a line for every hazard that is open again or due for review. Without a terminal, `spec-tacular` prints the overview as if `--print` were given.

## Setting up

### init

```bash
spec-tacular init [--force] [--driver <name>]
```

Installs the spec-tacular schema and the defect schema into `openspec/schemas/`, points `openspec/config.yaml` at it, scaffolds the Foundation, writes a starter `spec-tacular/verification.yaml` and writes `.spec-tacular/.gitignore`.

| Flag | Meaning |
| --- | --- |
| `--force` | Replace an existing install. Local edits to the schema are lost |
| `--driver <name>` | The agent `openspec init` must have been set up for. Default: `claude` |

`init` refuses, exit 1, when `openspec init` has not run in the folder, when it was not set up for the chosen agent, or when the schema is already installed and `--force` is missing.

### foundation

```bash
spec-tacular foundation
```

Shows the ground rules and what is still unanswered: `●` answered, `○` unanswered, `◌` left for later. Exits 1 when there is no Foundation yet.

## Drafting artifacts

### instructions

```bash
spec-tacular instructions <artifact> -c <change>
```

Prints the instructions an agent would get for writing an artifact: the project's context plus OpenSpec's instructions. Refused, exit 1, while the artifact's prerequisites are not accepted. Use it to feed a tool spec-tacular has no driver for.

### run

```bash
spec-tacular run <artifact> -c <change> [--driver <name>]
```

Dispatches an agent in the background to write the artifact, behind the same gate as `instructions`, and returns immediately. It prints the job id and its log path.

### jobs

```bash
spec-tacular jobs
spec-tacular jobs --job <id>
spec-tacular jobs --job <id> --cancel
```

| Flag | Meaning |
| --- | --- |
| `--job <id>` | Tail one job's output. A prefix of the id is enough |
| `--cancel` | With `--job`: stop a running job. Exits 1 if it is not running |

## Decisions and ground rules

### adr

```bash
spec-tacular adr
```

Lists the architectural decision records in `spec-tacular/decisions/`, with their status. Promote one while reviewing a design: :key-cap{k="p"} on a global decision.

### classes

```bash
spec-tacular classes
```

Prints the consequence class map, the rules each class turns on, and the class of every change. A change raised above its declared class shows `(declared <class>)`. Without a `classes.yaml`, it prints an example to start from and exits 0. See [Consequence classes](/docs/advanced/consequence-classes).

## Implementing and archiving

### diff

```bash
spec-tacular diff <change> [--accept]
```

Prints the implementation diff: the code changed on the branch. Required reading for a P0 change.

| Flag | Meaning |
| --- | --- |
| `--accept` | Record that you read and accept the diff as it is now. A later change to the code sends it back |

Exits 1 outside a git repository.

### archive

```bash
spec-tacular archive <change> [--dry-run]
```

Merges the accepted requirements into `openspec/specs/` and diverts the deferred ones to `spec-tacular/pending-validation.md`. Writes the change's `review.md`, runs `openspec archive`, and adds its accepted risks to the hazard register.

| Flag | Meaning |
| --- | --- |
| `--dry-run` | Say what archiving would do, or why it is refused, and write nothing |

Archiving is refused, exit 1, while a requirement is neither accepted nor deferred, while a P0 change's implementation diff is not accepted, or, where `verification.yaml` is set up, while any accepted item has no current evidence.

### pending

```bash
spec-tacular pending
```

Lists the requirements waiting on validation: accepted, deferred, and not in the baseline.

### verify

```bash
spec-tacular verify <capability> --requirement "<name>"
```

Moves one pending requirement into the accepted baseline, `openspec/specs/<capability>/spec.md`, then runs `openspec validate` on it.

| Flag | Meaning |
| --- | --- |
| `--requirement <name>` | The requirement's name, as `pending` lists it |

### roadmap

```bash
spec-tacular roadmap
spec-tacular roadmap --promote <slice>
spec-tacular roadmap --done <slice>
```

Shows the vision and the slices, and the next one to promote. Without a `roadmap.yaml`, it creates one to fill in.

| Flag | Meaning |
| --- | --- |
| `--promote <slice>` | Make a slice active |
| `--done <slice>` | Mark a slice finished |

### defect

```bash
spec-tacular defect <name> [--description "<what went wrong>"]
```

Starts a defect change with the defect schema. Its report decides first whose bug it is, and its first task is a reproducer that fails on the code as it is. Exits 1 if the defect schema is not installed: run `spec-tacular init --force` first.

| Flag | Meaning |
| --- | --- |
| `--description <text>` | What went wrong, in a sentence or two |

## Evidence and hazards

### evidence

```bash
spec-tacular evidence [<change>] [--run]
spec-tacular evidence -c <change> --sign <item> --method <m> --note "<what was checked>"
spec-tacular evidence -c <change> --waive <item> --reason "<why>"
```

Prints the verification matrix: each requirement and risk, how it is verified, by which tests, and its state. See [Verification evidence and CI](/docs/advanced/verification).

| Flag | Meaning |
| --- | --- |
| `--run` | Run the tests from `verification.yaml` first and append the results to the evidence log |
| `--sign <item>` | Record an analysis, inspection or demonstration of an item |
| `--method <m>` | With `--sign`: `analysis`, `inspection` or `demonstration` |
| `--note <text>` | With `--sign`: what was checked |
| `--waive <item>` | Waive an item |
| `--reason <text>` | With `--waive`: why |

Item ids are shown by `spec-tacular evidence <change>`. Without a `verification.yaml`, it explains how to write one and exits 0.

### hazards

```bash
spec-tacular hazards
spec-tacular hazards --reviewed <HAZ-n> [--note "<text>"]
```

Prints the hazard register, each hazard's status by its guards' latest results, and which are due for review.

| Flag | Meaning |
| --- | --- |
| `--reviewed <HAZ-n>` | Record that you looked at a hazard today |
| `--note <text>` | With `--reviewed`: a note added to the hazard's history |

## Formal requirements

These commands are covered in [Formal requirements](/docs/advanced/formal-requirements).

### glossary

```bash
spec-tacular glossary
```

Lists the variables formal requirements use, which requirements use each, and what is missing: variables used but not defined, and variables without a source, which cannot be observed or monitored.

### matrix

```bash
spec-tacular matrix [<change>] [--write]
```

Generates the test matrix of each formal requirement and prints it, with how many rows the change's class requires to pass.

| Flag | Meaning |
| --- | --- |
| `--write` | Write the matrices to `spec-tacular/matrix/`, copy the runner into the project and write a table-driven test per matrix. Names the harnesses still to write |

### harness

```bash
spec-tacular harness [<change>] [--check] [--allow-survivors "<why>"] [--accept]
```

Shows whether each matrix's harness reaches the real code.

| Flag | Meaning |
| --- | --- |
| `--check` | Run the matrix tests with coverage, then with mutants of the code they ran, and record the result |
| `--allow-survivors <why>` | Allow the changes no matrix caught, with a reason. Not allowed for a matrix that caught none |
| `--accept` | Accept the harness bindings you have read, as the review would |

### fret

```bash
spec-tacular fret check [<change>]
spec-tacular fret export [<change>] [--out <dir>]
spec-tacular fret realizability <project> <component>
```

| Subcommand | Meaning |
| --- | --- |
| `check` | Compare spec-tacular's reading of each FRETish requirement with NASA FRET's own formula |
| `export` | Write the FRETish requirements and the glossary for FRET. Default directory: `spec-tacular/fret/export` |
| `realizability` | Run FRET's realizability check on a FRET project and component |

| Flag | Meaning |
| --- | --- |
| `--out <dir>` | With `export`: where the files go |

`realizability` needs `fret.cli` set in `verification.yaml`, or `SPECTACULAR_FRET_CLI`.

### monitor

```bash
spec-tacular monitor <trace.jsonl> [<change>]
```

Checks a recorded run, one JSON object of variable values per line, against every formal requirement whose variables it records.
